## 1. 本期目标与承接关系

四期为已受管应用增加数据库与数据一致性、版本化备份、恢复和离线跨服务器迁移，并完成供后续正式上线复用的 Windows 更新/卸载安全核心。生产更新/卸载执行器、官网和发布下载链已经明确移入六期，不再作为四期完成条件。备份能力服务于恢复和迁移，但“生成归档”“校验归档”“恢复文件”“运行验证”必须是不同状态。

本期在三期的生态和多组件基础上，追加一体化桌面部署、AI 缺项补全、原生数据库管理、动态工具链、临时构建与独立运行身份，以及模块职责和失败契约修正。生产官网、正式发布下载和 Windows 独立维护执行器仍归六期。

沿用现有 Java 21、Swing、FlatLaf、主题和中英文机制，将桌面工具改为面向新手的一体化自动程序。用户选择源码和服务器后，一次启动完成常规部署，不再逐步点击分析、检查、环境准备和发布。单应用与多组件共用首页及现有部署事务、失败恢复和持久化机制。本期不开发 Web 业务。

### 3.1 桌面交互与高级帮助

**涉及模块与分工：** `app/ui` 负责表单和展示，`app/service` 转换输入及构造秘密记录，`app/main` 装配。

当前首页与备份页已接入服务门面。主题/语言切换保存输入和侧栏状态；完整 Swing 逐项点击、真实 AI 与数据库组合验收仍未覆盖。

#### 部署首页

- 上方左侧为源码选择：本地目录或 Git 地址；中间显示部署方向；右侧选择已保存服务器，支持就地添加。
- Git 默认解析仓库默认分支并固定到具体提交；分支、标签、提交覆盖放在高级侧栏。所有组件使用同一次源码快照。
- 添加服务器主要填写地址、用户名和密码；SSH 端口默认 22。保存资料不等于主机已受信。
- 只保留一个“一键部署”主按钮，单应用与多组件均自动识别并执行，不暴露必须逐个点击的阶段按钮。
- 底部日志始终可见并具有足够高度，追加真实阶段、结果和异常；不能使用假进度或结束后才一次性打印全部过程。
- 成功后在日志区域突出显示可复制的网址或目标服务器启动命令，网址支持打开。多组件汇总各组件入口；全部必要组件和整应用检查成功后才显示整体成功。

#### 高级参数与帮助

- 每页提供默认收起的右侧高级侧栏；展开不覆盖主要操作与结果。保留现有高级参数，不因收起改变参数或已保存部署语义。
- 有自定义参数时显示提示；页面、语言和主题切换保留输入及侧栏状态，程序重启默认收起。
- 每个高级参数旁放圆圈问号，鼠标悬停或键盘聚焦可阅读：用途、何时需要修改、默认/留空行为、修改影响。
- “高级选项”按钮旁同样提供解释。帮助使用白话及示例，禁止仅重复参数名。
- 所有静态 UI 文案必须通过 `MessageCatalog` 及中英文消息映射表读取，包括按钮、帮助、状态、补全选项和 DB 冲突。翻译显示与协议值分离；两个消息表的键和命名参数同步，架构测试拦截直接写入控件的文案。
- 原多组件人工编辑从部署页高级侧栏进入，保留组件及依赖调整能力。

| 页面 | 默认显示 | 右侧高级区域 |
| --- | --- | --- |
| 已部署应用 | 应用列表、状态、访问入口、启动/停止/重启 | 服务标识、运行参数、详细诊断 |
| 服务器 | 服务器列表、连接资料、保存并检查连接 | SSH 端口、凭据存储、环境详情 |
| 备份与恢复 | 备份/恢复/迁移任务选择与必要输入 | 归档检查、候选状态、资源和技术详情 |
| AI 配置 | 接口地址、模型、密钥、保存 | 多 Provider、角色分配、调用诊断 |
| 设置 | 语言、主题、使用说明 | 诊断路径、技术信息 |

备份、恢复主操作自动衔接检查和准备；停写、覆盖等必要确认仍明确展示。

### 3.2 一体化单应用与多组件部署

**涉及模块与分工：** `app/service.deployment.automatic` 统一编排；共享分析、计划、事务和远程执行复用已有类型化契约。

代码路径：[DesktopApplicationFacade.java](../../src/app/service/src/main/java/gold/debug/windowstolinux/app/service/DesktopApplicationFacade.java) 的 `deployAutomatically` → [AutomaticDeploymentUseCase.java](../../src/app/service/src/main/java/gold/debug/windowstolinux/app/service/deployment/automatic/AutomaticDeploymentUseCase.java)。获取服务器操作锁，固定本地/Git 快照，发现组件、补齐及校验输入，验证受信服务器，再选择单组件或整应用事务。自动准备数据库和环境仍受审阅与批准约束；最终状态来自事务结果。

后续环境准备与语言版本选择按 [动态工具链](PHASE-4.md#toolchains) 实施。单/多组件及 DB 参与流程传递相同的版本需求和解析结果；安装、源码或运行失败保留实际原因，不能统一改为版本不支持。

流程：固定源码快照 → 识别应用及组件 → 补齐信息 → 检查服务器 → 准备运行环境和数据库 → 构建、初始化、启动 → 健康检查 → 展示结果。

应用服务层新增统一编排入口；UI 仅收集输入和呈现进度。复用类型化分析器、部署计划、远端固定协议、失败恢复与受管持久化，不创建第二套部署引擎。项目清单、声明、已有运行时建议是识别入口、端口及组件关系的依据；多个候选或冲突不得任意选择。

点击“一键部署”授权本次常规环境准备和发布，首次主机信任及数据库替换等高风险操作另外询问。指纹变化继续拒绝。后台执行不得阻塞 Swing 事件线程；重复点击不能发起重复任务。任务期间固定输入，补齐后重新校验并继续同一次任务，取消停止后续步骤。

#### 缺项处理

1. 已接入 AI 时先请求补全。有源码依据、通过确定性校验的非秘密参数自动采用。
2. 未配置 AI、超时、返回无效建议或仍有缺项时弹窗；多个缺项自动组织成表单。
3. 弹窗右侧可展开 AI 问答，解释当前问题、填写方法和示例；未配置时提供配置入口并保留表单。
4. AI 问答不能执行命令；密码、卸载授权、无依据参数不能由 AI 代填或批准。上下文脱敏，不发送秘密和完整源码。
5. 失败、取消、恢复中、等待人工处理分别表达；失败不能显示成功入口。

最小接口：统一部署请求与结果、缺失字段与回答、结构化 AI 建议及问答、服务器列表、真实阶段进度通知。所有数据继续通过现有类型、路径、资源归属与秘密边界校验。

### 3.3 AI 缺项补全与确定性复核

**涉及模块与分工：** `shared/ai` 返回结构化候选，`app/service` 限定缺项及校验，`app/ui` 让用户补全或确认。

缺项先由确定性事实、用户已有输入和可验证默认值解决。AI 只为列出的字段提供候选；类型冲突、健康与访问 URL、配置、秘密引用和数据库范围仍由服务层校验。无 Provider、建议无效或调用失败时转人工表单，不能绕过必要批准。

敏感值不进入普通上下文，Provider 选择不因失败跨服务回退。现有调用链已接通；真实 Provider 与自动 UI/DB 的整体验证未覆盖，不能以模拟测试替代。

完整缺项流程见[自动部署](#automatic)，网络读取和日志边界见[来源与安全](#security)。

### 3.4 数据库识别、准备与管理

**涉及模块与分工：** `shared/analyze` 提取声明，`shared/model` 表达需求与审阅；`app/service` 补全认证、审批和保存绑定；`shared/linux-sshd.execution.protocol.database` 执行原生数据库协议。

现行入口：[AutomaticDatabaseUseCase.java](../../src/app/service/src/main/java/gold/debug/windowstolinux/app/service/deployment/automatic/AutomaticDatabaseUseCase.java)，由桌面门面调用并把 `NativeDatabaseException` 转为应用服务失败。凭据标识的 SHA-256 用作内部合法键段，外部秘密引用和修订保持原义。数据库安装/复用、版本替换与结构变化必须分别确认；数据库可准备不代表完整备份可用。

#### 结构与范围

DB 的模型、分析和远程契约仍使用 `ecosystem.db`；SSHD 固定执行实现归 `execution.protocol.database`，两个 native helper 片段归 `execution/protocol/helper/fragments/database/`。该规则替代早期四模块统一套包及 SSHD 根 `db` 布局，不调整其他共享模块或 `build.ecosystem`、`capability.ecosystem`。数据库仍不属于语言构建或桌面本地 SQLite 存储。以下分类适用于保留技术生态层的模块：

- `ecosystem.db.sql`：PostgreSQL、MySQL、MariaDB。
- `ecosystem.db.document`：文档型分类；本轮不实现 MongoDB 自动安装，也不创建空适配器。
- `ecosystem.db.other`：Redis。

分析、领域模型、Linux 契约和 SSHD 执行分别留在既有对应模块，遵循功能分组规范，不新增独立 Maven 模块。

#### 检测、安装与复用

默认直接安装到所选服务器系统，使用受支持发行版的固定适配，不默认使用容器。

| 服务器状态 | 行为 |
| --- | --- |
| 已有同类型且兼容版本 | 复用，不重新安装；缺少连接/管理凭据时弹窗 |
| 已安装但停止运行 | 检查现有实例，不认定为未安装 |
| 多个实例 | 弹窗选择复用目标 |
| 已有版本不兼容 | 暂停，展示现有版本、项目要求及替换影响 |
| 未安装所需类型 | 安装兼容版本，创建应用数据库/账号或 Redis 访问配置 |
| 类型冲突、来源或版本不明确 | 说明并询问，不静默替换 |

版本优先遵循项目声明。未声明时优先复用已安装兼容版本，否则使用适配器支持的系统仓库版本。不得自动替换数据库种类，不把较新版本简单视为不兼容。生成的凭据通过现有秘密存储保存，仅将引用注入配置；不得进入日志或 AI 上下文。

#### 用户批准旧版本替换

- 备份由用户自行完成。必须确认已备份、已做好停机准备并明确同意卸载旧版、安装目标版。
- 审批绑定服务器、实例及版本组合，执行前重新检查；事实变化使审批失效。
- 不自动清空旧数据目录，不自动恢复用户数据。需要恢复时等待用户恢复，再检查并继续部署。
- 替换软件包与恢复数据是不同状态，不得显示“安装完成”等于“数据恢复完成”。安装和升级受数据库支持路径限制：[PostgreSQL](https://www.postgresql.org/docs/current/upgrading.html)、[MySQL](https://dev.mysql.com/doc/refman/8.4/en/upgrade-paths.html)。

#### 新库初始化与已有库保护

- 只对本次创建、归属明确、可证明为空的应用库自动初始化。
- 支持明确选定的 SQL 初始化文件和受支持运行时中声明的初始化入口；无法确定入口时补问。
- 现有源码迁移标记全局拒绝改为结合目标库状态及初始化计划判断，不能简单移除安全检查。
- 初始化使用限定于应用库的权限，保存执行记录；失败重试不得重复初始化已有数据。

- Redis、多数据库依赖均进入资源清单。现有备份无法覆盖时明确拒绝“完整备份”，不得遗漏资源后声称完整。

#### 职责与扩展接口

#### 单一支持目录

`shared/model` 使用独立、只读、类型化的纯 Java 工具链目录，按生态组织分支、发布类型、维护状态、安装方案标识和必要兼容约束，不增加配置解析依赖。它是构建支持范围唯一来源。分析器、领域运行时、脚本和 helper 不再分别维护版本白名单。

版本数据与行为分离：同一安装或构建适配器服务多个版本，不为每个版本创建类。上游改变命令参数、制品格式或兼容约束时，才增加对应生态的实际行为分支。目录只引用已实现方案，不接受任意脚本或命令模板。

最小契约：

- `ToolchainRequirement`：原始声明、来源、解析后的要求和用途。
- `ToolchainSupportCatalog`：允许使用的分支、候选选择及兼容约束。
- `ResolvedToolchainSet`：实际精确版本、可信安装位置、来源证据、目录修订标识。
- 环境准备契约接收需求并返回实际选择和重新探测结果。

版本解析及比较按生态处理，不能用一个 SemVer 正则替代 Java `8u`、Go 最低版本、Rust channel 等语义。数字排序不得使用字符串字典序。

模型归 `shared/model`，声明解析归 `shared/analyze`，匹配及尝试编排归 `shared/deploy`，窄远程契约归 `shared/linux`，探测、安装及脚本归 `shared/linux-sshd`。工具链按实际功能组织；不新增 Maven 模块。具体目录同步 `File.md` 及架构门禁。

#### 识别、选择和兼容尝试

识别阶段保留所有合法版本声明，包括过旧、未来、非 LTS 和预发布版本；不受构建清单限制。复杂表达式无法确定时保留原文、来源和待补项，不执行项目脚本来猜版本，不让 AI 决定支持范围。

候选规则：

1. 要求在清单内且可满足时直接选择。
2. 清单外要求选择不低于声明的最近受支持分支；确认兼容性失败后最多再尝试一个更高分支。

### 3.6 构建隔离、运行身份与资源恢复

**涉及模块与分工：** `shared/deploy` 拒绝 root 构建请求并组织事务；SSHD 工作卷和运行协议实施边界；配置及持久化记录精确身份。

现行门禁：[ReviewedDeploymentService.java](../../src/shared/deploy/src/main/java/gold/debug/windowstolinux/shared/deploy/execution/transaction/ReviewedDeploymentService.java) 在远端修改前拒绝 `runAsRoot` 或非 root 管理连接。普通构建使用 DynamicUser；容器构建使用临时账号和受限 UID/GID 映射；普通运行与构建身份独立，容器应用显式使用非 root 用户。代表性部署已实测，完整资源攻击/UID 复用/故障注入矩阵仍未执行。

root 负责环境、发布和生命周期管理。普通构建使用 systemd 动态身份；容器 rootless 构建使用任务专属临时账号及 UID/GID 授权，完成后撤销。原生应用使用独立动态身份；容器应用必须明确以非 root 身份运行。临时身份不持有 sudo、登录权限或永久应用归属，不删除用户已有账号。“不创建永久账号”仅指本工具的项目/构建账号；数据库等系统包自带服务账号遵循其安装机制。

源码上传前预留固定容量 ext4 构建卷，挂载在既有候选 mutable 路径，缓存、日志、临时文件和容器构建存储均受限。收尾验证进程退出、制品封存、挂载和 loop 设备释放、临时账号与映射删除；失败隔离残留并明确报告。动态运行状态由 StateDirectory 与受控私有路径映射承载，秘密使用服务专属只读交付。旧部署仅在下一次受控部署中迁移，并保存可恢复的单元、数据布局和权限。

当前代码版本为 helper v7、桌面 SQLite v12、运行时和备份配置编码 v3；旧记录缺失的身份策略不得猜测。SSH 标准指纹仅在已认证的同一公钥证据下迁移。工具链精确版本必须包含构建号。发布成功但清理失败须登记实际发布并报告待清理项。

旧容器迁移先验证停止，保存数据布局与权限快照，再按明确受管范围调整；失败恢复旧状态。保留已存在账号和用户数据，不能将“低权限构建”表述成能证明任意不可信代码绝对安全。

**涉及模块与分工：** `shared/source` 排除敏感源码，`shared/git` 管理子进程；`shared/ai` 限制模型输入输出，SSHD 校验传输、SQL 客户端和发布权限。

### 3.8 生命周期、发布结果与连接收尾

**涉及模块与分工：** `shared/linux-sshd` 复核 unit、进程和控制组；`shared/deploy` 保留真实发布结果，服务层完成持久化；`app/main` 仅调整测试侧 NIO 收尾。

显式 STOP 在确认受管 unit 仍 loaded、MainPID 为 0 且控制组为空后，才可清除该 unit 的 failed 标记并重新查询。LoadState、控制组、停止结果或 reset-failed 查询失败都返回失败，不能把未知当成停止成功；不执行全局 reset-failed。

发布身份已经确认但版本保留或候选清理失败时，保持已发布事实并报告待清理项；不把成功发布隐去或伪装成已回滚。服务状态必须来自远端观测，SQLite 缓存不代替当前事实。

Windows NIO 修复仅针对验收用 SSH 服务的 accept/执行器关闭和异常归集，生产 SSH 客户端没有因此改动。原始失败和 suppressed 收尾失败同时保留。确切 Yarn 复验与本地 NIO 证据见[生命周期验收](#acceptance-lifecycle)。

### 3.9 模块职责、协议与失败契约

**涉及模块与分工：** `shared/linux` 只依赖 `shared/model`；deploy 负责配置投影，服务层负责 UI 输入解析；SSHD 的原生数据库归执行协议。

### 3.10 备份输入、归档格式与一致性

**涉及模块与分工：** `shared/backup` 定义归档和一致性；`app/db` 保存精确输入，`app/secret` 处理秘密，`app/windows` 管理材料及最终文件；服务层调用远程取材。

真实产品链：备份页 → 桌面门面 `createManagedBackup` → [RemoteBackupCreationUseCase.java](../../src/app/service/src/main/java/gold/debug/windowstolinux/app/service/backup/RemoteBackupCreationUseCase.java) → Linux 备份/数据库窄端口。当前 [BackupConfigurationCodec.java](../../src/shared/backup/src/main/java/gold/debug/windowstolinux/shared/backup/format/BackupConfigurationCodec.java) 写激活配置 v3，运行时编码器也为 v3。SQLite 完整远端备份因缺少已审阅物理路径而在连接前拒绝；多数据库超出归档单数据库范围，Redis 等管理能力不能推导为已有一致性备份。

#### 备份输入

备份开始前必须形成结构化数据清单：当前发布清单、普通配置快照、密钥引用元数据、持久化文件/卷、数据库类型与连接引用、运行身份、系统服务/容器定义、语言运行时、目标架构和恢复步骤。

未知路径、共享目录归属不明、外部数据库没有受支持导出方式或应用无法进入一致状态时，停止备份并说明缺失项；不能用直接复制伪装一致性备份。

桌面 SQLite v12 只从成功部署时仍持有的已审阅请求保存完整非秘密运行时定义、文件绑定、数据库绑定和独立整应用健康探针，并在同一成功事务中把实际使用的不可变普通配置修订及秘密引用与发布身份精确绑定。多组件文件绑定从 `ComponentDataPath` 形成稳定标识；发布时 helper 将其绑定到固定 Linux 受管根，逻辑源码路径只作为发布内符号链接位置，不会变成任意远端路径。数据库审阅支持 SQLite、PostgreSQL、MySQL 和 MariaDB：服务器数据库只保存端点、库名、用户名、TLS 要求和精确密码 `SecretReference`，绝不保存密码值。SQLite 当前只保存文件名，尚无足以证明物理位置的应用相对路径，因此完整远端备份在连接服务器前显式拒绝 SQLite，不猜测目录。数据库状态区分未知与显式空集合，绑定变化进入发布身份摘要。v10 及更旧整应用健康字段保持缺失；v9 及更旧资源字段保持缺失。

自动部署以源码声明、DB 清单、确定性校验和必要补填形成已审阅资源范围；已有数据库优先复用，替换和已有库结构修改分别明确确认。没有 DB 声明及迁移标记时记录显式空范围。高级手工单/多组件表单仍默认“尚未审阅”，必须明确选择无 DB 或连接绑定。Redis 增加非秘密资源序列化类型，但没有完整备份适配；Redis 或多数据库绑定均在远端备份前拒绝。语言/主题重建保留选择和引用，密码不进入普通状态；SQLite 物理映射仍未开放。

桌面第六个 `BackupApplicationFacade` 先执行不连接服务器的受管输入准入检查：逐组件核对整应用图、当前发布、运行时、文件/数据库范围、精确配置、秘密绑定和应用级健康探针，并通过二次读取拒绝状态漂移。输入完整后，用户可选择目标归档并输入独立备份密码及凭据存储主密码；门面自动使用已保存服务器资料，不要求用户重填 SSH 参数。`persistedInputsComplete` 只表示允许继续远端检查，最终成功仍必须完成远端取材、原运行状态恢复、两级健康、归档校验和最终位置复验。

#### 数据库范围

- SQLite：停止写入并使用 SQLite 在线备份 API 或经过验证的一致副本；禁止在活跃写入时直接复制数据库文件。
- PostgreSQL：使用版本匹配的受控逻辑备份/恢复流程，记录服务器和工具版本。
- MySQL/MariaDB：使用版本匹配的一致性逻辑备份/恢复流程，记录事务和非事务表限制。
- 其他或外部托管数据库：默认只记录人工恢复要求，不宣称已备份；新增正式适配必须另行确认。

涉及数据库结构变化的发布必须在本期定义显式迁移前检查、备份点、执行证据和回滚兼容性。不可逆迁移没有经过验证的恢复路径时不得自动发布。

#### 包结构

备份以单个版本化归档交付，至少包含：

```text
manifest.json          # 格式版本、应用/组件、来源、架构、文件清单和算法
releases/              # 需要保留的发布产物或可重建源码信息
config/                # 普通配置快照
data/                  # 受管持久化文件/卷导出
database/              # 受支持数据库的一致性导出
runtime/               # 运行时、unit/容器定义和能力清单
secrets.enc            # 用户选择包含秘密时的独立认证加密成员
```

- `manifest.json` 使用明确 schema 版本，未知必需字段或未知重大版本时拒绝恢复。
- 每个成员记录大小和 SHA-256 等内容摘要，用于损坏检测和传输校验。
- 普通摘要可以被攻击者连同内容一起重算，因此不得把“摘要匹配”描述为可信来源证明。
- 归档若提供独立数字签名，才可以在签名密钥可信的前提下声明来源验证；没有签名时界面只显示完整性检查结果。

#### 备份秘密

- 默认排除所有原始秘密，只保留不可用于解密的引用元数据。
- 用户选择包含秘密时，必须设置独立备份密码；平台主密码、Windows Credential Manager 和 Web 主密钥不能代替或被导出。
- 使用带独立随机盐和记录参数的 Argon2id 派生备份密钥，以 AES-256-GCM 等认证加密保护 `secrets.enc`。
- 密码、派生密钥和可等价恢复的材料不进入归档、平台数据库、日志或任务事件。
- 旧密码错误、认证标签失败或参数不支持时停止秘密恢复，不返回部分明文。
- 桌面和 Web 通过同一 `shared/backup` 格式交换加密成员，具体密码输入和解密只发生在各自 `secret` 模块。

桌面 `app/secret.crypto` 当前使用严格规范二进制明文载荷保存最多 64 个唯一“秘密标识 + 正修订号”精确引用；相同标识的不同修订可同时存在，重复的精确引用或非规范顺序会被拒绝。秘密值不进入不可清零字符串，认证后仍会严格检查格式、UTF-8、长度、顺序、精确唯一性和尾随字节。service 对 schema v4 只在全部解码成功且精确引用集合与 manifest 完全一致时返回一个整体可关闭的 `ResolvedSecretRevision` 文档；对 schema v3 只执行旧标识集合认证，不据此授权自动激活。错误密码、认证失败、格式错误、缺少成员或引用不一致均不返回部分秘密，并清零密码、关闭部分修订、清理本次候选。

桌面备份页面现可显式选择“验证密码并准备”：密码输入框立即清空，字符数组由 service 在成功或失败后清零；UI 后台任务只读取已认证修订数量，并在回到 Swing 事件线程前关闭整个秘密文档。页面只接收不含秘密的候选及数量，`BackupPageState` 不保存密码、解码修订或秘密引用。该结果只证明所选本地归档的密码与完整加密成员匹配，不代表秘密已传输或远端恢复已执行。

#### 归档安全

创建和恢复必须限制成员数、单成员/总解压大小、路径长度和压缩比，并拒绝绝对路径、`..` 穿越、越界符号/硬链接、特殊设备、重复覆盖和大小不符。先在受管候选目录完整校验，再允许进入恢复流程。

桌面当前通过独立 `BackupApplicationFacade` 提供不会连接服务器的本地产品入口：完整校验所选归档，或重新校验后在平台持有的 `work/restore-candidates` 下创建新的摘要绑定隔离候选，并可删除页面当前持有的精确候选。候选根在安全提取前必须不存在；工作区签发不可伪造尝试并绑定父目录创建时文件身份，删除前重新核对工作区、精确父子关系、目录类型和身份，重建对象、工作区外路径或外部替换均失败关闭且保留内容。页面一次只跟踪一个当前候选，删除失败保留身份以供重试，语言或主题重建携带同一内存删除授权；应用重启后不猜测或扫描旧目录。界面明确本地准备或删除都不等于远端恢复或激活。

完整归档产品入口先在同服务器互斥锁下权威观察全部组件，只停止原本运行的组件；随后按依赖顺序收集发布树、普通文件 PAX TAR、命名卷 PAX TAR、Docker/Podman OCI Archive 和固定数据库逻辑制品。两个容器引擎均要求可验证的 OCI 导出与显式目标导入；能力缺失时拒绝，不在恢复阶段以 root 重建项目。无论取材成功或失败，入口都会恢复原本运行的组件并执行逐组件和整应用健康；无法证明恢复时返回 `MANUAL_RECOVERY_REQUIRED`。`app/windows.workspace` 在固定工作根保存本次成员，再由用户目标同目录临时文件完成写入、完整校验、无覆盖原子移动和最终路径独立复验；目标已存在、成员摘要不一致或外部替换均失败关闭且不越界删除。

```text
查询受管身份和实时状态
→ 生成数据/数据库/秘密清单
→ 选择并展示一致性策略及停机影响
→ 停止写入或进入经过验证的一致性模式
→ 导出数据库和文件
→ 创建归档、摘要和可选加密秘密
→ 在独立位置重新读取并校验
→ 恢复应用原运行状态
```

- 同服务器重装前必须确认至少一个已完整读取校验的副本位于本机之外或另一服务器。
- 备份失败时恢复原运行状态；恢复失败进入人工处理并保留中间证据。
- “备份创建完成”不等于“恢复演练通过”，界面分别显示创建、完整性、解密可用性和恢复验证状态。

### 3.11 受管恢复与离线迁移

**涉及模块与分工：** `shared/backup` 定义状态机，`shared/deploy` 处理候选和正式提交；`app/service` 连接备份、秘密、数据库、远端恢复与本地接管。

桌面 `restoreManagedBackup` 已调用 [ManagedRestoreUseCase.java](../../src/app/service/src/main/java/gold/debug/windowstolinux/app/service/backup/ManagedRestoreUseCase.java)；离线迁移由 [ManagedOfflineMigrationUseCase.java](../../src/app/service/src/main/java/gold/debug/windowstolinux/app/service/backup/ManagedOfflineMigrationUseCase.java) 组织初始备份、明确停写批准、最终备份和目标恢复。成功后等待人工切流，保留源端，不自动删除或切换流量。真实数据库恢复与双服务器迁移仍为 RUNTIME-PENDING。

#### 前置检查

恢复前校验格式、摘要/签名状态、备份密码、目标发行版/架构、运行时、数据库版本、端口、路径、空间和现有受管应用冲突。源码型备份优先在目标机重新推导环境并构建；二进制恢复必须展示兼容性结论。

#### 候选恢复

- 所有内容先进入新的受管候选目录和临时数据库/命名空间，不能直接覆盖当前成功版本。
- 数据库和文件恢复完成后启动候选，执行组件健康和整体业务健康。
- 只有全部验证成功才提交当前指针；失败则删除明确归属的候选或保留诊断，不破坏现有版本。
- 明确不兼容的二进制不提供强行启动；跨发行版/主版本的未知兼容只能在用户确认后作为试验候选。

当前平台无关实现使用同一操作标识依次记录前置检查、文件暂存、候选数据库、组件健康、整体健康、提交和恢复证据。schema v4 在 schema v3 的源发行版/版本、14 种封闭运行时、依赖顺序、定义成员引用、组件探针和整应用健康门之上，要求每个组件携带发布 SHA-256 与精确秘密修订；应用级 `releaseSetSha256` 由固定域、组件数量和依赖顺序中的“组件标识 + 发布 SHA-256”按长度分隔计算，应用秘密集合必须等于组件引用并集。恢复适配器把这些身份交给 deploy，deploy 独立重算摘要与并集后才接受请求。未知运行类型、额外命令字段、乱序依赖、错误摘要、非规范秘密引用或缺失定义成员直接拒绝。schema v3 仍可确定性读取、本地检查、准备候选并认证旧秘密标识，但在任何远端暂存或激活前失败关闭；schema v4 声明秘密却排除固定唯一 `secrets.enc` 时同样不能自动激活。平台无关恢复模型区分源码与二进制兼容策略；当前桌面受管恢复上传归档中的精确制品，不将该模型能力宣传为已接通任意源码跨架构重建。二进制恢复要求架构精确一致，其他差异仍受目标预检约束。数据库恢复一旦开始，即使适配器尚未返回成功证据也执行幂等候选清理；文件清理或现有发布复核不完整时终态固定为 `MANUAL_RECOVERY_REQUIRED`。

当前具体实现已将 schema v4 归档成员、配置文档 v3 及精确激活身份单向映射到 deploy 和 Linux 恢复契约；SSHD 只创建摘要派生候选目录，经 SFTP 上传精确成员，并再次回读逐项核验大小和 SHA-256，暂存过程不寻址当前发布。目标预检在任何写入前检查受管冲突、能力、空间、架构、数据库工具/版本与端口策略。容器以及静态站点、PHP、Ruby 的显式监听端口可在 `49152-65535` 分配回环候选端口；其余运行时使整应用采用短停机，不允许用新旧混合图冒充健康。秘密、配置和制品暂存后才执行数据库实际连接及候选恢复；候选两级健康仅是提交前预检，正式提交恢复正式端口和服务身份后再次执行组件与整应用健康。任一失败必须清理候选并验证旧发布恢复，否则进入 `MANUAL_RECOVERY_REQUIRED`。远端正式健康后才登记目标秘密和本地整应用图，并单独报告本地接管是否完成或延后。以上为产品组合静态实现，真实 helper v7、Linux 和数据库执行仍为 `RUNTIME-PENDING`。

迁移采用明确停写窗口，不声称在线无损切换：

```text
预检查目标机并完成初始传输/构建
→ 用户确认停机窗口
→ 停止源应用写入并确认静止
→ 生成最终数据库和文件一致性增量/快照
→ 校验并恢复到目标候选
→ 启动目标并执行整体健康验证
→ 用户手动切换 DNS、代理或其他外部流量
→ 用户确认目标业务正常后结束
```

- 系统不自动接管 DNS、域名、负载均衡或云安全组。
- 目标验证失败时停止目标候选并重新启动、验证源应用。
- 外部流量切换后失败时，界面给出回切步骤，但必须由用户确认外部状态后执行源端恢复。
- 未得到用户确认不得自动删除源端应用、数据或旧版本。
- 迁移结果分别记录源停止、最终同步、目标恢复、运行验证和外部切换状态。

桌面双服务器产品用例把目标归属、能力、端口、兼容性和两副本空间检查置于任何目标写入之前；先从仍运行的源端创建完整初始备份，只有用户明确批准停写窗口后才停止源应用并证明无活跃写入，再创建最终停写完整归档。最终归档摘要绑定目标候选并复用同一受管恢复链。目标正式健康完成后只返回 `READY_FOR_MANUAL_TRAFFIC_SWITCH`：源端保持停止但不删除，最终归档保存在 `data/backups`，系统不修改 DNS、代理或其他外部流量。源端整应用图仍作为权威归属保留时，目标本地接管明确标记 `DEFERRED_SOURCE_RETAINED`，不制造两个“当前”图。任何失败都分别验证目标候选清理和源端恢复；未批准停写时不建立 SSH 会话或执行远端操作。以上为产品组合静态实现，真实双服务器执行仍为 `RUNTIME-PENDING`。

<a id="maintenance"></a>

### 3.12 桌面更新与卸载安全核心

**涉及模块与分工：** `app/windows` 验证更新、回滚与受管卸载请求；`app/secret` 删除精确凭据；外部执行器与生产产品入口归六期。

#### 更新来源和签名

- 更新元数据和安装包必须通过固定发布信任根验证数字签名与版本，不接受仅有 HTTPS 或摘要的未签名包。
- 禁止降级、未知签名、过期/撤销发布和架构不匹配；紧急回退必须使用同样签名且经用户确认。
- 下载先进入受管临时目录并完整校验，不能覆盖正在运行的程序。

#### 受控替换

```text
停止接收新任务
→ 等待任务进入安全终态或可恢复状态
→ 备份应用 data/SQLite 和版本信息
→ 主程序退出
→ 独立更新器替换程序文件
→ 执行版本化数据库迁移并启动健康检查
→ 成功提交；失败则恢复旧程序和旧数据库
```

更新器不接触明文秘密或实现另一套加密逻辑。`data` 固定位置和用户选择的凭据存储模式升级前后保持一致。数据库回滚必须使用升级前备份，不能尝试让旧程序读取已失败迁移的新结构。

当前安全核心使用严格三段式版本、固定架构、签名有效期、撤销集合和 Ed25519 公钥策略验证已暂存包；摘要只证明内容绑定，只有固定信任根签名通过才产生更新验证证据。等版本和未批准降级拒绝；紧急回退同时需要签名清单标记与用户明确批准。事务已拆分为主进程 `prepare` 和独立更新器 `apply`：前者只停收任务并成对备份程序/SQLite，后者只有在验证更新器身份、主进程退出和交接真实性后才允许替换。主进程交接已可编码为严格有界、版本化、用途隔离且经 HMAC-SHA256 认证的文档；认证通过前不解析领域载荷，错误密钥、篡改、截断、跨用途重放和认证后畸形载荷均失败关闭。编解码器不持有调用方密钥；数据库迁移或新版本健康失败仍必须同时恢复旧程序与迁移前 SQLite。仓库未嵌入测试私钥或伪造生产公钥。生产信任材料、官网/发布下载、独立执行器和实际产品接线属于六期，详细方案在六期实施前另行确定。

- 每次卸载都要求用户明确选择“保留数据与凭据”或“删除本应用数据与凭据”，不设置默认选项。
- 删除前停止本应用任务并校验 jpackage 安装根、固定 `data` 目录、受管标记和专用 Credential Manager 命名空间。
- 不删除用户项目源码、下载到其他位置的备份、目标 Linux 应用或其他程序数据。

#### 已复现问题

> 历史记录：仅证明下列版本、环境和夹具的结果，不作为当前工作区的新验证。

##### 环境准备脚本超过 Linux 单参数限制

首次 `UbuntuManagedEnvironmentSetupAcceptanceTest` 失败：`/bin/bash: Argument list too long`。失败发生在脚本启动前，软件安装尚未开始。当时 helper 含完整多段脚本，被拼接进 `bash -lc` 单个参数，超过目标机限制。

修复：`SshCommandExecutor.execScript` 经标准输入传输完整命令组，使用 Bash `-s` 读取；命令组重定向到 `/dev/null`，防止安装器读取后续脚本文本。环境准备改用该入口，既有协议载荷输入仍使用原入口。新增本地 SSH/Bash 回归，覆盖超过 128 KiB、中文和引号、子命令读输入、非零退出码、独立协议载荷。

依据：[Linux execve 参数限制](https://www.man7.org/linux/man-pages/man2/execve.2.html)、[GNU Bash 的 -s 输入方式](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html)。修复后同一服务器连续两次环境准备通过。

##### 旧验收步骤断言类型不匹配

当时 `DeploymentEvent.step()` 为 `DeploymentTraceEvent` 枚举，8 个旧真实验收类仍将其直接与字符串比较。改为比较 `step().code()`，避免成功步骤被误报缺失；这项检查修复本身不构成部署成功证据。

##### Kotlin 系统包不满足产品版本要求

Ubuntu 仓库安装的 Kotlin 包为 `1.3.31+ds1-1ubuntu1`，实际命令报告 `kotlinc-jvm 1.3-SNAPSHOT`；产品需要 Kotlin 1.9/2.x 与 Java 21。环境准备现在保留系统编译器，必要时下载独立的 Kotlin 2.0.21，先校验官方 SHA-256，再安装到产品专用目录。能力探测和构建使用同一个选择器；重试复用已完成安装。

官方校验值：`0352c0a45bd22f80f6b26e485cd04da8047baa5de54865281fb9f89a4a7bcf2a`，来源为 [JetBrains 发布附件](https://github.com/JetBrains/kotlin/releases/download/v2.0.21/kotlin-compiler-2.0.21.zip.sha256)。

APT 安装明确使用非交互前端，`needrestart` 仅列出待重启服务，避免自动重启已有业务；诊断输出在脱敏后保留头尾，防止大量安装日志挤掉末尾失败检查码。

##### 配置保存精度与顺序导致本地应用登记回滚

首次 Node.js 远端发布和 HTTP 成功，但生命周期报没有受管应用。离线新增用例复现：先保存含纳秒时间、非键序条目的配置，成功部署登记时再次保存，同一对象因 SQLite 毫秒精度和键序读取被 `equals` 错判为修改不可变修订，整个登记事务回滚。现在按已验证的规范内容摘要和毫秒时间比较，仍拒绝内容或存储时间改变。秘密修订元数据重复保存也按相同存储精度核对，并保留凭据引用、模式和时间不可变检查。

首次部署观察记录改为在应用登记之后保存。实机测试现要求成功结果没有非致命告警，并能从本地产品清单找到应用，不再只断言远端终态。

##### JVM 默认内存预留与受限构建冲突

在同机对 JDK 21 执行 3 GiB 虚拟地址空间限制，`javac -version` 和 `jar --version` 均因 native thread 创建失败而无法启动。明确约束堆、元空间、压缩类空间和代码缓存后，同一限制下两项命令通过。JVM 构建脚本按用户给出的上限生成有界设置，保留 `ulimit`；修复后 Java 源码完整发布/回滚测试通过，Spring Boot 已构建、发布并通过外部 HTTP 检查。

##### 防火墙状态探测修正

同机只读检查显示 `systemctl is-active ufw` 为 active，而 `LC_ALL=C ufw status` 为 inactive。前者是 oneshot 单元状态，不能代表实际规则状态。探测已改为读取 UFW 自身状态，普通权限失败时仅尝试非交互 sudo 的同一只读命令；权限不足或输出不明返回 unknown。Bash 回归覆盖启用、停用、权限拒绝、未知输出和 sudo 读取成功；没有启停防火墙或修改规则。

修复后通过产品入口断言 `managed.expect.firewall-state=INACTIVE`，实机结果与 UFW 自身一致。

##### npm 生成的命令链接与无符号链接发布规则冲突

TypeScript 已在目标机完成 `npm ci` 和编译，但第一次发布被 `MANAGED_HELPER_REJECT=source-symlink` 拒绝。npm 即使使用 `--ignore-scripts` 仍会生成 `node_modules/.bin` 命令链接。现在在构建后将此类链接转换为指向依赖树内真实可执行文件的可搬移命令脚本；保留目标位置和参数，先检查目标范围、存在性和可执行性，以临时文件原子替换。其他链接仍由原发布规则拒绝。

同机隔离回归已执行生产转换代码，检查含空格/引号的路径及参数在目录搬移后仍正确，越界、悬空和循环链接均被拒绝；临时目录自动清理。新增 Linux/macOS JUnit 回归，Windows 普通门禁条件跳过此真实链接用例。

##### 新增验收的 Windows HTTP 客户端初始化失败

C++ 和 Spring Boot 已发布成功，但新测试使用 `java.net.http.HttpClient` 时，Windows JVM 在创建 Selector 所需的本地连接中报 `UnixDomainSockets Invalid argument: connect`，尚未向目标应用发送 HTTP 请求。C++ 的服务器本机和 Windows curl 均返回 200/正确内容。测试改为复用既有验收使用的 `HttpURLConnection`，并保留连接、读取超时与显式断开；这属于本机测试执行问题，不算远端产品修复。

##### 容器标签模板转义与首次发布前的回滚

Docker 和 Podman 均完成镜像构建，但镜像归属校验中的单引号 Go 模板保留了多余的反斜线，引擎报 `unexpected "\\" in operand`。已修正镜像、卷及相同原因的备份卷标签查询，保持标签值和归属校验不变，并加入模板转义门禁。备份卷的同源修复不构成备份端到端成功证据。

该失败发生在应用目录创建之前，原首次回滚无条件要求应用根目录和 releases 目录存在，误报 `MANUAL_RECOVERY_REQUIRED`。现在允许这些目录尚未创建；若目录存在仍校验所有者及无链接边界，若存在 Docker/Podman 同名容器或 Quadlet 则拒绝自动清理。Bash 回归验证无目录回滚与两种引擎冲突拒绝。实机只读确认该次失败应用没有发布根目录、容器或 Quadlet，因此可以修复后继续产品部署，无需用户处理或重装。

此修复改变 helper 内容，20 段资源独立组装后的 SHA-256 为 `d7fd7ae66b0ddc17f08d78e7450cb08bc92418bccccc6a1abb58b18206764ce7`；11 个发行版安装脚本的固定身份同步更新。前面的语言验收使用相同协议 v5 的原 helper `ad6692acedf1749c663559c67e114c12525660d5eda048e751d6c21fd3ab2fa8`，新变更只涉及容器标签查询、容器首次回滚及同源备份卷查询。

##### 容器测试夹具的正常退出

初版 Python 容器夹具作为 PID 1 没有处理 SIGTERM，停止操作在 10 秒后以 SIGKILL 结束进程，Podman 单元因此保留 exit 137/failed；当时已核对 MainPID=0、容器不存在、临时转发规则已清理。没有将强制终止伪装成正常退出。现为夹具增加 SIGTERM 退出处理，并在容器完整验收结束时通过产品入口禁用自启和停止，再复测收尾状态。旧夹具的已停止单元仅对其精确名称清除 failed 记录。

新 Podman 夹具最终经产品停止后，同机只读核对 `Result=success`、`ExecMainStatus=0`、`MainPID=0`、`ActiveState=inactive`，且自启 drop-in 不存在。

### 生态构建直接验收方法

真实验收已固化为 `EcosystemExtensionProductEntryAcceptanceTest`，默认一次执行全部 12 种架构，也可用 `managed.runtime.extension.type` 选择架构键（如 `node-yarn`、`python-poetry`、`cmake`）。测试只调用桌面产品门面和 `SshdLinuxGateway`，不包含手工 SSH、systemd 或任意远端命令旁路。

```powershell
$env:JAVA_HOME='E:\Program\Java\JDK21'
$env:WINDOWSTOLINUX_TEST_SSH_PASSWORD='<由用户在本机设置>'
$env:WINDOWSTOLINUX_TEST_MASTER_PASSWORD='<由用户在本机设置>'
mvn.cmd -B -ntp -o -pl :windowstolinux-app-main -am `
  '-Dtest=EcosystemExtensionProductEntryAcceptanceTest' `
  '-Dsurefire.failIfNoSpecifiedTests=false' `
  '-Dmanaged.runtime.extension=true' `
  '-Dmanaged.runtime.extension.type=all' `
  '-Dmanaged.runtime.extension.prepare-environment=true' `
  '-Dmanaged.ssh.host=<服务器地址>' `
  '-Dmanaged.ssh.user=<登录用户>' test
```

现行入口必须使用 root 登录管理，禁止 `-Dmanaged.root-build=true`；普通构建与运行采用独立动态身份。发行版层准备系统依赖，语言工具链按四期动态工具链规范按需准备；包管理器依项目锁文件和选中语言版本在受限构建内准备。上传前检查隔离能力与空间预算，无法满足时前置拒绝。初始三期夹具版本范围见[三期历史生态验收](PHASE-3.md#acceptance-ecosystem)；当前工具链需求、选择和安装按本期实际代码执行。

##### 文件型备份、恢复和迁移自动验收入口

该入口不是底层 helper 测试。它创建临时桌面 SQLite，通过 `DesktopApplicationFacade → SshdLinuxGateway → managed helper v7` 生产组合根依次完成源码分析、部署、完整备份、目标恢复和离线迁移。两个测试使用随机应用标识及高位业务端口；一个验证源应用保留时的目标恢复，另一个验证源端停止、最终归档保留、目标健康和“等待人工切流”。

源端与目标端必须是两台授权写入且可保留测试应用的专用服务器，端口应能从开发机访问，并已分别通过 3.1 或 3.2 的当前 helper v7 环境准备复验。测试不会自动删除源端、目标端或替用户切换外部流量；这正是产品安全边界。当前夹具显式审阅“无数据库”，因此只证明普通文件/发布制品链，不能替代 PostgreSQL 或 MySQL/MariaDB 的数据库矩阵。

```powershell
$env:JAVA_HOME='C:\Program Files\Java\latest\jdk-21'
$env:WINDOWSTOLINUX_TEST_SSH_PASSWORD='<源服务器密码>'
$env:WINDOWSTOLINUX_TEST_TARGET_SSH_PASSWORD='<目标服务器密码>'
$env:WINDOWSTOLINUX_TEST_MASTER_PASSWORD='<临时桌面数据库主密码>'
$env:WINDOWSTOLINUX_TEST_BACKUP_PASSWORD='<至少 12 个字符的独立备份密码>'
mvn.cmd -B -ntp -o -pl :windowstolinux-app-main -am `
  '-Dtest=ManagedBackupRestoreMigrationAcceptanceTest' `
  '-Dsurefire.failIfNoSpecifiedTests=false' `
  '-Dmanaged.backup-restore-migration-acceptance=true' `
  '-Dmanaged.ssh.host=<源服务器地址>' `
  '-Dmanaged.ssh.port=22' `
  '-Dmanaged.ssh.user=root' `
  '-Dmanaged.target.ssh.host=<目标服务器地址>' `
  '-Dmanaged.target.ssh.port=22' `
  '-Dmanaged.target.ssh.user=root' test
```

普通离线门禁不设置 `managed.backup-restore-migration-acceptance`，两个测试必须显示为跳过；一旦启用，任何缺失秘密、服务器资料、登录失败、归档失败、恢复失败、源端状态错误、目标 HTTP 失败或错误终态都必须使 Maven 失败。正式证据取自完整命令、Surefire XML、结构化 operationId 和目标环境观测，不能只记录进程退出码。

##### 完整备份与受管恢复桌面入口

通过桌面“备份”页面执行，禁止用测试代码、直接 SSH 或 helper 命令代替：

1. 输入已经成功部署并保存在当前 `data/windowstolinux.db` 的应用标识，先执行只读输入检查。
2. 创建完整备份时选择最终归档路径，输入独立备份密码及凭据存储主密码；记录原运行状态恢复、组件健康、整应用健康及最终归档复验结果。
3. 恢复时选择 schema v4 完整归档和已保存的目标服务器，输入独立备份密码及凭据存储主密码；先查看目标零写入预检，再由同一后台任务完成候选、数据库、健康、正式提交和失败恢复。
4. 记录候选模式（回环并行或整应用短停机）、正式提交后的二次健康、本地秘密登记和整应用图接管状态。远端成功而本地接管失败时不得只记录为普通失败。

每次验收使用全新应用标识或经审阅的专用目标。当前产品不能从 SQLite 绑定创建完整远端备份，不能通过手工构造归档绕过该拒绝。

##### 双服务器离线迁移桌面入口

通过同一桌面“备份”页面选择受管源应用、已保存的目标服务器、初始及最终归档位置，并明确确认停写窗口：

1. 未确认停写时必须证明没有建立 SSH 会话或执行远端操作。
2. 确认后先创建源端运行态初始备份，再停止并验证源端无活跃写入，随后创建最终停写完整归档。
3. 目标恢复复用 3.4 的正式链路；失败必须分别记录目标候选清理和源端恢复证据。
4. 成功终态必须是 `READY_FOR_MANUAL_TRAFFIC_SWITCH`。测试人员手工处理外部流量；软件不得自动切流、启动回源或删除源端。
5. 源端保留期间目标本地接管可为 `DEFERRED_SOURCE_RETAINED`，这是防止双重权威图的明确限制，不是可忽略的警告。
