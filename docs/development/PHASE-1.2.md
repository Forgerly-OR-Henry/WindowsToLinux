## 3. 功能规格与已确认决定

<a id="file-management"></a>

### 3.1 主 APP 通用文件 API 与访问范围（已确认规格）

#### 已确认的功能定位

文件资源与 SSH 连接是 APP 的基础能力。主 APP 通过统一 API 提供本机 Windows 与已连接 Linux 服务器上的通用文件操作，供 APP 内部调用方和 Mod 复用。1.2 不提供资源管理器式的目录树、文件列表及可视化浏览操作页面，也不开发资源管理器 Mod；后续由该 Mod 调用平台 API 提供界面。

`file` 模块负责通用文件能力与规则，任务、授权和资源归属接线归 `app/service`；本功能不向 `app/ui` 新增文件管理页面。活动资源模块已经迁为 `src/app/file`，公开接口为 `appapi/file`。业务 Mod 继续决定使用哪些文件、如何解释内容及何时执行业务操作。

#### 已确认的访问范围

- Windows：跟随运行 APP 的账户及 APP 进程实际获得的权限。账户可访问的文件属于平台 API 可访问范围；读取、写入和删除分别以实际权限为准，不额外限定只能访问某个选定根目录。
- Linux：跟随 SSH/SFTP 登录账户及该会话实际可访问的文件范围，遵循远端权限和服务器对会话的限制；平台不自动提升权限。
- 系统权限决定文件操作的权限上限，既有 Mod 调用授权、任务绑定和资源归属继续生效。受管工作目录、快照和明确授权的任务资源仍保留各自边界，不能将它们的局部目录约束当作整个通用文件 API 的统一根目录限制。
- 无权列举、读取、写入或删除时，接口返回对应失败；有权读取不表示同时有权修改。取消、有界读写、容量和资源释放规则继续保留。

| 能力组 | 已确认纳入文件管理的范围 |
| --- | --- |
| 目录查询 | 通过 API 列出目录和文件、获取属性，支持重新查询及约定的排序与筛选；不包含可视化浏览页面 |
| 基本操作 | 文件和目录的新建、重命名、复制、移动、删除；目录操作应覆盖内容处理，不能仅支持空目录 |
| 内容读写 | 读取文件内容、保存生成内容，通过统一能力供 APP 内部调用方和 Mod 使用 |
| 本机与远端传输 | 上传、下载，复用进度、取消及已有传输恢复机制 |
| 既有受管能力 | 保留受管资源自身的路径边界、有界访问、摘要、快照、工作目录和资源释放，并与统一入口衔接 |

上述常用操作均纳入 1.2，可按小批次实现，但不能只交付查询或读写后把复制、移动、删除留待以后。文件能力的基线覆盖 Windows 本机、单台已连接 Linux 内部，以及本机与远端之间的上传下载；跨两台远端服务器的复制/移动不纳入本期基线，后续扩展按第 7 节处理。目录列举是 API，不新增资源管理器或完整编辑器；本轮也不推定新增任意系统权限管理、归档工具或跨服务器原子事务。

<a id="file-conflict"></a>

#### 复制、移动的同名冲突与方法重载（已确认规格）

复制和移动仍分别提供**同名方法重载**，以是否传入冲突处理方式区分交互。按下方 `File` / `Link` 对象约定明确方法名；对象不同的入口不替代各自的重载。以下只示意调用形式，参数类型和返回值在 S3-01 落实：

```java
copyFile(from, to, task);          // 操作实际对象，冲突时由平台询问
copyFile(from, to, task, choice);  // 按明确传入的目录/文件策略处理
moveFile(from, to, task);
moveFile(from, to, task, choice);

copyLink(from, to, task);          // 操作链接本身
copyLink(from, to, task, choice);
moveLink(from, to, task);
moveLink(from, to, task, choice);
```

**目录复制采用两步交互。** 本规则承接同名冲突场景：目标存在同名目录时先决定目录如何处理；目标尚不存在时正常创建并复制，不询问没有实际冲突的“合并”。复制/移动共用冲突分类，目录移动沿用相同选择，仍保留成功后才清理对应源的移动语义。

| 步骤 | 用户选择 | 已确认行为 |
| --- | --- | --- |
| 第一步：同名目录处理 | 复制为副本 | 保留原目标目录，为输入目录生成不冲突的新名称并复制其内容；返回实际新路径，不进入原目录的合并流程 |
| 第一步：同名目录处理 | 合并 | 进入第二步，比较目录内容；递归合并同名子目录，保留目标独有内容，不先清空或整体替换目标目录 |
| 第一步：同名目录处理 | 不处理 | 不修改该目录对应的源和目标，该次操作返回失败并说明用户选择不处理；不进入文件冲突比较与执行 |
| 第二步：合并中的同名文件 | 覆盖 | 仅替换本次明确的同名文件；保留写入、校验后发布及执行前目标重验，不先删旧目标再冒险写入 |
| 第二步：合并中的同名文件 | 保留副本 | 保留已有目标文件，为输入文件生成不冲突的新名称并返回实际路径 |
| 第二步：合并中的同名文件 | 不处理 | 保持该冲突项源和目标不变，该项失败并注明用户选择不处理；继续其他独立文件，最终报告部分失败，不报全部成功 |

选择目录合并后，先比较并取得冲突文件的处理决定，再修改这些冲突文件；目录层“合并”不等于已经批准文件层“覆盖”。无文件冲突的内容按合并规则正常处理；文件与目录同名但类型不同不能直接套用目录合并或先删除后重建，应明确报告类型冲突。目录内已完成部分、取消与失败按真实结果返回，不承诺整棵目录事务回滚。

普通文件的直接复制/移动沿用第二步的覆盖、保留副本、不处理三种选择。移动选择目录或文件副本时仍执行移动，不变成保留源文件的复制；只有对应目标写入并校验成功，才清理对应源，不清理未处理或失败的源项。

未传 `choice` 时，由平台在实际冲突层级询问。显式策略须分别表达目录的副本/合并/不处理，以及文件的覆盖/副本/不处理，不能用一个“覆盖”值隐含替用户选择目录整体替换。已明确的层级不重复询问；只明确目录合并而未明确文件冲突方式时，文件层仍交给用户选择。两层均明确时按策略执行，不重复弹窗；显式参数的非法值应拒绝，类型和缺省表达在 S3-01 统一。

冲突处理方式属于业务选择，**不等于文件访问权限或免审批许可**。各个入口与重载均保留任务、调用方、账户权限、平台授权及实际对象身份校验；受管传输路径也要保留明确传入的方式，同步调整此前“一律弹出同名选择”的旧约定。

覆盖授权对应替换该文件，移动授权对应将源移至目标；这两种完整操作不再额外转入普通删除的确认弹窗，也不把旧目标或成功移动后的源自动当作用户主动删除的回收项。跨文件系统移动先核对目标写入和校验成功，再清理对应源；源清理失败不得报告移动完成。覆盖失败、断连或结果未知时保留真实状态，不用删除后重试掩盖失败。普通复制/移动授权不能挪作任意其他对象的删除许可。

**目录执行顺序与实际对应关系：** 先确定目录及文件冲突方式，建立本次源对象与实际目标名称的对应关系，再执行文件操作，随后完成依赖目标的链接，最后汇总结果。目录可分批遍历和执行，元数据及结果有界；需要用户决定的冲突项获准前不修改。保留副本导致名称变化时，链接必须使用实际新名称，不能根据原名称猜测。进入目录后不跟随子链接复制目录外内容。

| 执行情形 | 已确认处理 |
| --- | --- |
| 用户对某一冲突文件选择不处理 | 该项源和目标保留；其他独立项继续，整体返回部分失败 |
| 已知单项错误，例如无权读取 | 该项失败；没有依赖且仍可安全执行的项继续，依赖失败项的步骤不执行 |
| 链接所依赖的内部文件被跳过或复制失败 | 不发布该链接副本，报告关联目标未完成；不误指向目标目录里原有的同名文件，不悄悄退回原件 |
| 连接断开、授权失效或副作用未知 | 停止受影响的后续操作，先核对；未获证据前不继续依赖步骤或盲目重发 |
| 取消整个任务 | 停止新增操作并收尾，分别记录已完成、未完成和未知项 |

整体沿用 `OperationResult`：全部完成为 `SUCCEEDED`；有用户跳过或已知失败时为 `FAILED` 并携带部分结果；用户取消且副作用可确认时为 `CANCELLED`；仍有不明副作用时为 `UNKNOWN`，不能被取消或已知失败掩盖。结果提供实际位置、各项结果和原因的汇总及有界明细，不新增仅为表示部分完成的平行结果体系。“等待用户处理”是未完成流程状态，不提前返回成功或取消。

<a id="file-link"></a>

#### 实际对象与链接对象的 API 命名（已确认规格）

用户已明确使用两个简单词区分操作对象：**`File` 表示实际文件或目录；传入链接时操作它实际指向的目标。`Link` 表示链接对象本身。** 用 `readFile` / `readLink`、`copyFile` / `copyLink`、`moveFile` / `moveLink`、`deleteFile` / `deleteLink` 等名称表达区别，具体签名纳入 S0 的公开 API 清单及 S3-01 合同。

这里的 `File` 是公开名称的对象语义，不要求改用 `java.io.File` 或放弃既有受管引用；普通文件和目录均属于通用文件能力。`Link` 指本轮讨论的符号链接、平台支持的目录联接点，不自动扩展为所有特殊文件或重解析点类型。仍由同一个文件模块和受管服务实现，不新建 Maven 模块或绕开任务的底层客户端。

| API 类别 | 操作对象与结果 |
| --- | --- |
| `readFile`、`writeFile` 等内容操作 | 操作实际文件内容；输入为链接时先解析实际目标，按目标类型、权限及资源边界执行 |
| `copyFile`、`moveFile` | 复制/移动实际目标；指向目录时按上方目录规则处理，不悄悄改成复制/移动链接对象 |
| `deleteFile` | 删除实际目标；传入链接时须明确显示目标及删除效果，不把只删链接当作删除目标成功，也不顺带删除指向该目标的链接 |
| `readLink` 等链接查询 | 读取链接自身的信息和指向信息，不读取目标文件内容；查询和解析目标内容是不同能力 |
| `copyLink`、`moveLink`、`deleteLink` | 操作链接本身，不递归处理它指向的目录，也不复制、移动或删除目标内容；返回实际链接对象的结果 |

`Link` 复制/移动遇到同名链接对象时，按单项的覆盖、保留副本、不处理规则执行；不能因为链接指向目录就进入目录合并。源和目标位置都需核对实际对象类型，未获对应授权时不能将普通目录或目标内容替换为链接。

`File` / `Link` 区分的是**操作对象**；普通/前置许可、交互/明确冲突方式区分的是**同一操作的调用形式**。两者分别表达，不能混为“File 是普通权限、Link 是高权限”，也不能因新增对象名称而取消已确认的同名重载。

调用前先确定并展示本次实际对象：常规确认、AI 用途说明和前置许可均对应实际将被操作的对象；涉及链接时标明输入链接路径及其指向信息，实际目标不可解析时明确标为断链或相应状态。许可须绑定 File / Link 语义、主机及对应对象。File 操作在执行前重验解析链和实际目标身份；Link 操作重验链接自身身份和指向记录，不以实际目标必须存在或可访问作为操作链接本身的前提。不能用批准删除链接的许可删除目标，也不能在确认后操作已被替换的对象。

对于读取、复制/移动源、删除等要求既有对象的操作，File 入口遇到断链、解析循环、对象不存在或无权访问时明确失败。新建文件/目录及复制/移动的新目标路径允许尚未存在，按相应创建合同检查父目录、权限和路径身份，不能被“目标不存在就失败”一律拦截；已有链接断链不等于已经批准在它指向的位置新建内容。Link 入口可按自身权限处理一个目标不存在的有效链接，不因断链切换成其他文件操作；普通对象误传 Link 入口或底层不支持时明确失败。

**整个目录内部的链接已经确认按 Link 处理。** 复制目录时复制内部链接，移动目录时移动内部链接，删除目录时只删除其中链接，不跟随它去复制、移动或删除外部目标。若显式传给 File 入口的根参数本身是链接，仍先操作其实际目标；进入目录后发现的子链接则按 Link 处理。源和目标目录遍历均须识别链接，不能借合并穿过目标内部链接修改外部内容；类型冲突按既有规则报告。保留原权限、资源边界及循环检查。

**链接按操作种类维护，范围仅限 APP 文件操作。** 判定依据是操作是否经 APP 的统一文件 API 发起，包括 APP 自身和 Mod 调用；不以最终执行移动的是哪一个系统函数或命令判断。APP 调用 Windows 原生能力或 SSH/SFTP 时仍执行本节规则。Windows 资源管理器、Linux 命令行、其他程序及未接入文件 API 的任意脚本独立操作，由系统自行处理；APP 不监听、不拦截、不补改链接，也不扫描命令内容推断移动。

| 经 APP 文件 API 发起的操作 | 已确认链接规则 |
| --- | --- |
| 移动或重命名原文件 | 更新受管链接为原件的实际新位置 |
| 复制单个原文件 | 原有链接仍指向原件，不改到副本 |
| 单独复制或移动链接 | 新位置的链接仍指向原目标，必要时调整相对地址 |
| 复制同时含文件和链接的整个目录 | 副本中的内部链接指向副本里的对应文件，使用实际复制成功后的名称；原目录及其中链接保持不变 |
| 目录内链接指向目录外 | 保持原来的外部目标，不跟随复制或修改目标内容 |
| 移动同时含文件和链接的目录 | 按实际移动结果维护关联；外部未移动目标保持原位置。目录未整体移完时，指向整个源目录的链接不能提前改到不完整的目标目录 |
| 用新文件覆盖链接指向的旧文件 | 链接继续指向该目标路径并打开覆盖后的内容；受管记录同步新目标身份，不再登记成尚未替换的旧对象 |

覆盖的规则适用于明确批准的目标替换，不改动指向复制来源的链接，也不复用旧对象的删除许可。File 入口的实际目标、Link 入口的链接对象、整目录内部链接处理仍按上文区分；不能因覆盖跟随路径就取消执行前的身份和授权检查。

维护范围为 **APP 已登记的链接，以及本次操作明确纳入的链接**，不是系统里所有可能指向同一对象的链接。登记/解除沿现有受管资源入口实现；登记不授予额外写权限，单纯列目录或读取链接也不自动授权修改。执行前核对维护清单、链接身份、当前指向、账户权限及任务授权；外部改动、失效记录或无权更新均明确报告，不能按旧记录强行覆盖。结果标明实际维护范围，不声称修复未登记链接。

原本已经断开的链接仍可按 Link 合同复制/移动：保留原所指位置并标明断链，不擅自创建目标。它与“本次应复制的内部目标却未复制成功”分开处理，后者按上表执行失败规则，不发布误导性链接。相对或绝对地址由适配器按已确认指向生成；跨卷、跨主机或协议限制导致无法表达指向时，尽可能在副作用前拒绝相关操作，不改成传输目标内容。目录链接链按实际映射核对，不递归遍历到目录外。

移动只有在目标写入并校验成功后才清理对应源项；未处理和失败的源项保留。目录及关联链接不承诺整体原子完成：能提前发现无法维护则先失败，执行中失败/取消/未知则分别记录文件及链接结果。“文件已搬走、链接未更新”不是全部成功；只有源目录整体迁移完成才完成目录级指向更新。

<a id="file-operation-records"></a>

#### 受管记录与中断核对（已确认规格）

复用现有数据库、任务与恢复设施，区分两类最小记录，不建设全盘索引或后台跟踪服务：

| 记录 | 必要内容 |
| --- | --- |
| 链接关联 | 主机、链接位置及身份、指向、归属、最后确认状态 |
| 操作依据 | 操作 ID、原任务、源和实际目标、冲突决定、受影响链接、执行阶段及逐项已知结果 |

**先保存操作依据，再执行有副作用的动作。** 文件移动、链接更新与记录提交分别核对；已确认完成的阶段不在重试时重新执行。仅有操作记录不代表仍有有效许可，重开后不能恢复旧内存许可或越过原调用方边界。

| 中断位置或现状 | 核对与继续规则 |
| --- | --- |
| 尚未开始移动 | 核对原操作确未执行，重新检查条件及授权后才可继续 |
| 文件已移动、链接未更新 | 核对原件的新位置和原链接身份，保留未完成状态；明确发起继续并获有效授权后，只处理未完成部分 |
| 链接已更新、记录提交未确认 | 核对真实链接符合原操作事实后补齐记录，不再次移动文件或重写已正确的链接 |
| 无法确定文件或链接是否变化 | 保持 UNKNOWN，等待核对，不自动重放 |
| 对象已被其他程序改变 | 报告冲突，不按旧记录覆盖现状 |

APP 重启先保留待核对状态，不自动修改文件或执行剩余动作。沿用现有 `TaskRecovery` 的不重放合同：核对和补齐可证明的原结果，与明确授权后执行尚未完成步骤分开；不在恢复回调中重跑整套移动。仅能证明的阶段才结清，记录提交不明同样保留依据。

回收站搬移、覆盖暂存发布和临时文件清理属于各自操作的内部步骤，不能误触发普通移动的链接跟随。删除目标后不把原有链接改到回收站；按登记事实更新关联状态，不顺带删除其他链接。底层 Windows / SFTP 原语及链、跨卷支持由实施者核对，以本项目合同为准。记录所需数据直接纳入第 3.6 节当前新建库结构，S3 先用任务自有临时库验证，S5 再统一切换。

<a id="file-delete"></a>

#### 删除方法重载、用途说明与前置许可（已确认规格）

**每种操作对象分别采用同名删除重载。** `deleteFile` 操作实际目标，`deleteLink` 操作链接本身；各自不传许可时需要用户确认，传入平台签发的有效前置许可时免重复确认。两类入口共享必要的权限、任务和底层原语，不复制两套审批实现。以下示意调用形式：

```java
deleteFile(file, task);          // 实际目标：用途说明与用户确认
deleteFile(file, task, permit);  // 实际目标：校验前置许可后执行

deleteLink(link, task);          // 链接本身：说明与用户确认
deleteLink(link, task, permit);  // 链接本身：校验前置许可后执行
```

| 重载 | 调用与交互要求 |
| --- | --- |
| 常规 `deleteFile(file, task)` / `deleteLink(link, task)` | 删除前由平台弹窗，展示准确对象及可用用途说明；可回收时由用户选择“移入回收站”或“永久删除”，不可回收时确认是否永久删除；默认暂不处理，关闭同样保留对象并等待 |
| 高权限 `deleteFile(file, task, permit)` / `deleteLink(link, task, permit)` | 先核对有效前置许可及对象语义、作用域，满足条件后执行，不重复弹出删除确认；常规功能使用对应的无许可重载 |

<a id="delete-ai-setting"></a>

**设置项：删除前使用 AI 说明文件用途。** 在主 APP 设置中提供统一开关，默认开启；用户可为减少模型调用额度消耗而关闭。适用于常规 `deleteFile` 和 `deleteLink` 的用途说明，不控制删除确认、回收规则或工作流必要的独立 AI 审批，也不是免审批权限。

| 开关与模型情况 | 行为 |
| --- | --- |
| 开启，主模型调用列表有已启用模型 | 使用语言用途列表首个已启用模型生成用途说明 |
| 开启，但未配置可调用主模型 | 不发起说明请求，展示基础信息并保留删除确认；仅在通用清单登记过模型不算配置完成 |
| 关闭 | 不发起用途说明请求，不为说明读取内容片段；展示基础文件信息并保留删除确认 |
| 模型调用失败或超时 | 展示基础信息和失败原因，仍由用户确认，不自动换第二个模型 |

开关复用平台数据库的桌面偏好存储，作为当前 APP 配置保存，不只保存在控件或进程内存中；无需为一个布尔值新增独立数据库模块。首次初始化采用开启值，正常缺失键按默认开启处理，已保存的关闭值在重开后必须保留。非法值或数据库读取失败不得当作正常缺失触发模型调用：报告设置异常，跳过可选说明，继续按有效的原权限和人工确认规则处理，不静默覆盖设置。

保存沿已有后台设置服务和事务规则执行，成功后界面才显示已保存，失败如实提示，不把未提交值当作已生效。准备发送每次用途说明前检查有效开关；关闭成功后后续请求不再发出，已发出的请求不承诺可撤回或返还额度。

**常规删除中的 AI 只负责说明文件用途，不负责代替用户作删除决定：**

1. 开关开启且主语言模型已配置时，按语言用途调用列表的顺序选择第一个已启用模型生成简短说明。通用清单只登记和验证模型；用户须将模型加入实际主模型调用列表、启用并保存后才参与业务调用，不能取清单第一项，也不改用审批、视觉或语音用途。沿平台 AI 服务调用，不能无提示轮换模型。
2. 说明回答文件或目录可能用于什么、删除可能影响什么。以名称、类型、位置和可用元信息为依据；确需内容时只使用当前授权允许的有界、必要且经既有保护处理的片段，不为用途说明扫描整个目录或上传完整文件。文件内容是待分析资料，不能作为指令改变权限或触发操作。 `File` 删除说明围绕实际目标；`Link` 删除说明围绕链接用途、指向和入口影响，不为解释链接而读取目标文件内容。
3. 弹窗区分实际文件信息和 AI 推测，对无法判断的内容如实说明。AI 返回“可以删除”不构成批准，最终选择仍归用户。
4. 开关关闭或未配置主语言模型时不调用用途说明模型，展示基础文件信息及相应状态，仍允许用户确认；模型不可用、超时或分析失败也保留人工确认路径，不强制配置模型。说明调用有界等待，不占用界面线程；取消任务不继续请求或执行删除。
5. 用户允许后，重新核对文件身份和本次批准的实际效果再执行。拒绝、关闭或暂不处理时保留文件，说明对后续步骤的影响并暂停依赖步骤；用户处理后可显式继续并重验，或终止任务。不把拒绝当作成功，也不反复自动重试。
6. 用途说明与独立 AI 审批是不同调用。普通人工文件操作不因为用途说明失败而被阻断；若所属 AI 工作流本来要求独立审批，该工作流仍执行其规则，不能借常规重载绕过已经适用的审核。

<a id="delete-wait"></a>

**拒绝删除后的等待与继续。** 当前通用审批拒绝返回取消，新文件流程不能直接借此结束原任务。文件流程记录“等待用户处理”的状态和原因，并在平台任务界面提供以下操作；等待是未完成状态，不伪装成删除成功或任务取消：

| 用户操作 | 平台行为 |
| --- | --- |
| 继续 | 重新检查对象、依赖条件与授权；仍需删除时重新取得必要确认，不复用失效决定 |
| 终止任务 | 停止后续流程，保留实际结果并完成资源收尾 |
| 暂时不操作 | 保持等待，不反复弹窗或自动重试 |

等待不占用数据库事务，不保留无必要的文件句柄或网络请求；任务归属和保护未完成操作必需的记录保留。用户已从外部处理对象时报告事实，由原流程重新判断下一步条件，不伪造本 APP 已删除成功。当前运行内可继续原流程；重启后先核对待处理记录，业务继续沿原工作流恢复能力，不新增恢复任意 Java 调用栈的引擎，也不自动重发删除。高权限重载的无效许可仍明确失败，不自动转入此确认/等待流程。

**高权限重载要求明确的前置授权：**

- 只供已经具备相应权限的受管流程使用，例如 AI 完全控制任务中取得的许可。许可须由平台在本地校验、独立 AI 审批及适用人工规则满足后签发；仅有模式名、枚举、布尔值或调用方自称高权限均不足以放行。
- 许可绑定 File / Link 操作语义、原任务、调用方、本机/服务器身份、具体对象及允许的删除效果。File 操作包含需核对的解析链和实际目标身份；Link 操作核对链接自身身份及指向记录，不要求其实际目标存在。执行前重验并消费授权；不能把回收许可升级为永久删除许可，不能跨对象类别、跨任务、改目标或重复使用已消费的许可。
- 许可为空、伪造、失效、审批拒绝/不可用或权限不足时，返回明确失败且不删除；高权限重载不静默降为常规弹窗。调用方需要交还用户时，应显式走常规流程，并遵守已有审批拒绝与任务状态。
- 本地授权和独立 AI 审批在调用前完成；删除函数负责校验其有效性，不重新用“文件用途说明”冒充审批。满足条件后不再询问用户，也不为免确认调用增加用途说明弹窗。

**两种删除重载按各自确认/许可合同处理回收效果，共用文件归属规则：**

用户已有文件、用户主动新建的文件、软件生成后交付给用户的正式结果均按用户文件保护。只有平台明确登记、由受管任务管理且已核实身份的临时文件/目录允许按既有资源清理合同直接清理；不能仅凭名称带 `tmp`、所在目录或调用方声明判断。受管临时资源清理不是普通删除重载的免确认后门。

对用户持有的链接对象，`deleteLink` 同样遵循常规效果选择/有效许可规则；回收或永久删除的对象是链接，不跟随它去删除目标。`deleteFile` 传入链接时按实际目标适用回收与删除规则，说明可能使原链接失去目标，但不顺带清理链接；断链不能作为“实际目标已成功删除”的证据。

| 场景 | 行为 |
| --- | --- |
| Windows 用户文件或目录 | 可回收时常规重载让用户选择系统回收或永久删除；高权限重载仍验证前置许可并优先回收 |
| Linux 用户文件或目录 | 核对实际回收能力；可回收时常规重载让用户选择回收或永久删除，否则确认永久删除；普通 SFTP 删除不等于回收，不能假定服务器已有桌面回收工具 |
| 已核实的受管临时资源 | 按原任务归属及清理合同直接删除，不误删正式结果或越过资源边界 |
| 已知无法回收，尚未永久删除 | 常规重载明确告知不可恢复后果并取得针对永久删除的确认；原确认若仅允许回收，则须更新确认。高权限重载仅在许可已明确覆盖永久删除时执行，否则明确失败，不自行弹窗或升级权限 |
| 回收、删除或目录部分操作的实际结果未知 | 保留原操作及资源状态，先核对真实结果，不重复发送删除或静默改用永久删除 |

常规删除的许可必须绑定用户实际选择的效果；可回收对象也允许用户明确选择永久删除，不能用回收许可执行永久删除。高权限表示免重复询问，不表示一律永久删除；其前置许可仍在能够回收时优先回收，不能用永久删除意图绕过该规则。Linux 回收可优先评估通用 [Trash 存储规范](https://specifications.freedesktop.org/trash/latest/)，按当前账户、会话路径和文件系统条件保留可恢复信息；具体回收适配在实施时核对。**独立的回收项查询、还原 API 尚未由用户确认，不作为本期已经批准的必做接口。** Windows 也须核对回收结果；无法回收时适用上表规则。

现有两层授权继续保留：平台的一次/通用/完全授权决定实际操作作用域；AI 人工审核、自动审批、完全控制决定工作流审核方式。用户文件永久删除仍按高危操作处理，自动审批模式不能自行降低风险。任一层仍要求人工时不能调用免确认重载绕过；AI 完全控制也须具备平台作用域及已通过的本地、独立 AI 审批。

确认窗口由平台交互层呈现，底层文件实现不直接依赖 Swing；文件服务协调 AI 说明、权限与任务，主 APP 不反向依赖部署 Mod 私有审核实现。上述合同的实际实现与专项验证对应 S3 阶段验收。

既有确需物理目录的本机工具调用仍需明确边界。补齐能力时复用已有读取、快照和传输实现，避免各调用方复制通用文件操作；后续界面 Mod 也沿用同一公开入口。

<a id="ssh-structure"></a>

### 3.2 SSH、SFTP 与救援的职责和分包（已确认规格）

#### SSH 与 SFTP 共用连接基础，文件操作独立

SFTP 复用受管 SSH 会话，共用连接、主机身份校验、认证与加密传输；文件查询、目录操作、读写和传输独立放入 SFTP 包。现有 `SftpTransfer` 已接收 `ClientSession` 并在其上创建 SFTP 客户端，可复用这一实现基础，不重复建设连接和凭据管理。

SSH 命令通道与 SFTP 文件通道各自承担自己的操作和收尾；底层会话的归属与释放由连接管理统一协调。复用会话不改变原任务、服务器身份和授权范围，不向 Mod 暴露原始 SSHD/SFTP 客户端。统一 `FileService` 已通过平台服务接入受管 SFTP 文件能力，跨主机内容传输复用既有传输记录和恢复合同；现行公开接口及原 `RemoteSession` 文件方法的边界见 [Mod.md](../Mod.md)。

#### 已确认的目标包结构

以下省略 Maven 物理目录及固定 Java 包前缀，表示当前职责分组；完整实际目录见 File.md：

```text
app/
├─ linux/
│  ├─ ssh/
│  │  ├─ connect/       # 正常连接、认证、会话及命令执行
│  │  └─ recover/       # SSH 救援状态、会话与原任务恢复
│  │     ├─ ai/         # 救援专用模型、提示及响应协议
│  │     ├─ browser/    # 浏览器、终端及所属进程控制
│  │     └─ model/      # 共享目标、动作、探测与终端观测值
│  └─ sftp/             # 远端文件协议实现，复用 SSH 会话
├─ ui/
│  └─ server/           # 服务器配置、连接检查及救援对话框
└─ db/
   └─ sshrecover/       # SSH 救援记录、查询及归档
```

- Linux 下由 `ssh` 聚合正常连接与故障救援两个流程；`sftp` 与 `ssh` 并列，运行时仍使用 SSH 会话，均属于原 Linux Maven 模块。
- 救援通过浏览器访问网页终端，再复核 SSH 是否恢复，不要求另一条正常 SSH 连接已可用；正常连接不反向接管救援。
- 完整救援归 `app/linux/ssh/recover` 及上述职责子包；Service 和通用 AI 模块不保存专属救援包。数据库仓库及归档留在 `db/sshrecover`，平台能力由启动层注入，救援对话框归 `ui/server`。
- 通用任务恢复、凭据、任务调度、普通 SSH 和 Windows 窗口保护保持各自归属；`ui/task/TaskRecoveryPane` 继续是通用任务恢复页面。
- 子包依据实际职责确定，类型数量只触发检查，不为数量或目录对称增删包；迁移保持包内合作及可见性，资源定位与依赖方向均需核对。

<a id="ssh-rescue-entry"></a>

#### 服务器列表手动检查失败后进入救援

**现状已核实：** 默认主 APP 已装配服务器列表的“检查 SSH”和独立“SSH 网页控制台救援”按钮。救援服务已连接模型、专用浏览器、SSH 复核、任务清理和归档，不依赖部署流程或业务 Mod。检查失败结果现提供进入本次检查对应服务器救援的操作，启动前重新核对原资料、任务及资源边界；独立手动救援入口继续保留。实际验证见 S2。

**已确认新增流程：**

```text
在服务器列表选择服务器
→ 手动检查 SSH
→ 连接失败时显示原因及“进入 SSH 救援”
→ 用户点击后打开本次检查对应服务器的现有救援流程
```

该流程由主 APP 独立提供，不等待部署或外部 Mod 发现连接失败。保留现有手动救援入口，复用现有救援服务，不另实现一套救援状态机。

入口将救援目标绑定到本次检查的服务器，避免用户改变列表选择后启动错误目标；原检查完成必要收尾后再启动救援。认证、主机身份、连接失败、取消与未知结果按真实原因显示，不能把所有失败都当作可自动修复的连接故障，也不能跳过现有信任和授权边界。进入救援由用户点击触发，不因一次检查失败自动打开浏览器或执行修复命令。

现有救援仍要求用户登录相应云平台、选择正确网页终端并确认具体操作；恢复后通过主机身份、认证及固定只读命令复核 SSH，不自动继续原部署业务。计划编制时仅核对代码、既有测试报告和文档；本期新增衔接已执行本机回归，见 S2。真实服务器、厂商页面及 Linux 修复组合仍未验收，见[操作手册第 17.1 节](../PRODUCT-MANUAL.md)。

### 3.4 APP 简单命名、层级收敛与 Mod 自主组织（已确认规格）

#### 设计目的与层级口径

使用者希望通过常见、直观、容易记忆的英文名称理解 APP 结构，减少阅读长职责词和多重嵌套目录的负担。部分业务已交给 Mod 实现，APP 不应继续为这些业务预留详细分类，也不因旧模板而保留无独立作用的父包。

本次讨论区分 Maven 模块与模块内部的 Java 包。APP 的 `ai`、`db`、`linux`、`service` 等是模块；其下面的 `install`、`start`、`check` 等才是本轮要统一的内部包名。以下示例省略 Maven 的 `src/main/java` 以及固定 Java 包前缀，不表示修改 Maven 物理目录约定：

```text
app/
└─ mod/              # APP 模块
   └─ install/       # 模块内第一层功能包，使用 APP 命名规范
      └─ Xxx.java

mod/
└─ example/          # 一个业务 Mod，名称仅作示意
   └─ file/          # Mod 第一层职责包，与 APP file 模块对应
      └─ ...        # 作者自行组织；不规定内部词表和层级
```

#### AI 通用能力按功能归包（1.2 交付后调整）

通用 AI 代码采用 `model`、`vision`、`voice`、`http` 四个职责包：`model` 保存模型能力、用途、常规文字调用及共用消息协议；`vision` 保存图像格式/大小/整请求数量校验、视觉消息编码和视觉能力挑战；`voice` 保存完整音频转写、实时转写协议及会话；`http` 保存各调用共用的精确端点校验与有界响应读取。常规文字不另建 `text` 包，视觉继续复用共用模型调用，语音继续使用独立转写协议。SSH 救援的提示及结果解析归 `app/linux/ssh/recover/ai`，不并入通用能力包。

本次只调整内部职责和引用，不变更 `appapi` 合同、模型配置、数据库、请求载荷、调用预算和未知结果处理规则。实际目录与逐文件归属同步维护于 File.md 和 AllFile.md；本次回归结果与 1.2 原交付验收分别记录。

本次归包回归（2026-10-03）：JDK 21 下两批共 14 个不同测试类、110 项相关检查全部通过，零失败、错误或跳过；覆盖文字/视觉请求、跨消息图片数量上限、模型验证与路由、HTTP/WebSocket 音频转写、语音配置和公开服务、SSH 救援及结构门禁。12 个受变 Java 文件的 IDEA 格式检查、生产 AST/双语注释与 JDK 21 doclint 通过；AllFile 的 871 个生产 Java 路径与实际文件集合一致，冻结归档及其 Git blob 校验通过。视觉挑战由服务层适配到共用答案核验，包依赖无循环；验证进程使用既有仓库 `target` 临时目录约定，首次默认临时目录的 JDK 内部连接失败不计入通过结果。本次未重跑完整根测试，不增加真实模型提供方或远端验收结论。

<a id="public-api-names"></a>

#### 全部平台公开 API 的简单命名（已确认规格）

面向英语非母语开发者，优先使用常见、简短、容易理解的单词。盘点范围覆盖 `appapi` 自有公开包、接口/类/记录/枚举、方法、公开成员与参数；不是要求每个名称都必须改动，也不修改 JDK、JDBC、Swing 等外部标准 API 的既定名称。

1. **常见词优先。** 在含义同样准确时选择更简单的词；用少量常见词组合表达职责，减少冗长的名词串。不设置机械的字符上限，不靠生僻缩写、单字母或截断拼写压缩长度。
2. **短而明确。** 方法名结合所属服务表达动作，例如 `read`、`write`、`start`、`stop`、`check`、`open`、`close`。上下文已说明对象时避免重复堆叠前缀；确需区分目标、状态或返回值时保留必要限定。文件 API 已明确用 `File` / `Link` 区分实际对象和链接，例如 `copyFile` / `copyLink`、`deleteFile` / `deleteLink`，不能为缩短而抹去这一区别；取消信号访问器与执行取消也不能混用。
3. **保留必要区分。** `task`、`file`、`db`、`ui` 等清楚的名称继续使用。授权请求、已经签发的许可、任务与结果、引用与实际对象不能因为缩名而混为同一概念；不把“回收”和“永久删除”或“检查”和“执行”命名成无法区分的入口。
4. **符合 Java 标识符规则。** 不使用 `class`、`new`、`default`、`public` 等保留关键字，`true`、`false`、`null` 等字面量也不能用作标识符。上下文关键字和受限标识符按所在位置核对，例如 `var`、`record`、`yield` 的限制不能忽略；`open` 在普通方法名中合法，不因它在模块声明中有特殊含义就一律禁用。以项目 JDK 21 的编译结果验证，参考 [Java 标识符与关键字规范](https://docs.oracle.com/javase/specs/jls/se21/html/jls-3.html#jls-3.8)。
5. **遵循既有大小写与标准合同。** 类型采用现有大驼峰、方法和参数采用小驼峰；标准接口要求的覆盖方法名保持不变。不为短名引入类型重名、含糊重载或误导性的返回类型名称。
6. **一次同步迁移。** S0 列出“旧名 → 新名／保留 → 中文职责及理由”，S1 按可编译批次更新平台实现、调用方、测试、导出声明、规范和示例；不把普通命名选择再次交给用户逐项批准。不为本次开发期 API 改名额外添加旧名转发层。持久化值、序列化字段、协议标识及业务配置键是独立合同，不能随 Java 名称机械替换。

下表说明已落实的选词方式；其余公开 API 经实际签名和上下文盘点后保留清晰短名，完整清单见 S0 验收：

| 场景 | 简单命名示意 | 判断依据 |
| --- | --- | --- |
| 文件服务及其入口 | `FileService`、`file()` | 已确认映射，职责直接可见 |
| 取消信号类型及访问器 | `CancellationToken` → `CancelToken`；`cancellation()` → `cancelToken()` | 已迁移；保留“返回信号”与“执行取消”的区别 |
| 校验结果类型 | `ValidationReport` → `CheckResult` | 已迁移；调用方与结果含义同步 |
| 常用操作及对象区分 | `read`、`write`、`copyFile` / `copyLink`、`deleteFile` / `deleteLink` | 按职责选词；File / Link 属于必要语义区分，各自的交互/策略/许可差异仍用同名重载；新建可用 `create`，不能使用关键字 `new` |

这套规则由平台维护者落实到公开 API；Mod 作者调用改名后的平台入口，但其内部实现及自有公开 API 仍按原自主组织边界处理。简单命名不减少第 3.7 节要求的基础能力，也不改变任务、权限、数据和资源生命周期合同。

#### APP 默认减少层级

1. 默认只保留模块下面第一层必要的功能分类，具体实现可以直接放入该功能包；不为规则、执行、存储等标签反复增加一层。
2. 模块本身已准确表达单一职责、内部也没有实际分类需要时，类可以直接位于模块 Java 根包。后续同步取消“根包只能放入口、门面或公共契约，因此具体实现必须进入子包”的硬限制；根包位置不改变类型可见性与公开合同边界。
3. 只有实际独立功能、所有权、访问隔离或依赖边界需要时才增加子包；“默认一层”不是绝对禁止子包，也不靠文件数量和目录对称决定拆包。
4. `contract`、`generation`、`extension`、`execution`、`persistence` 不再作为 APP 必须套用的固定中间层。能由功能包直接表达的职责，优先省去容器；确有独立作用时再决定是否保留，不强求为五个词分别寻找短词。
5. 合并目录前核对包可见成员、类型重名、资源定位和依赖；对外接口、纯规则与 I/O、数据库访问与业务编排等边界仍需保留。不能把取消目录模板理解为取消职责约束。
6. 功能已交给 Mod 实现的，APP 不为其保留空目录或预设业务细分；平台继续提供通用能力和受管边界。

Linux 的 `ssh/connect` 与 `ssh/recover` 已确认为具有实际分组意义的结构，按第 3.2 节保留；DB 保留直接的 `sshrecover`，UI 救援归 `server`，不要求所有模块复制相同深度。

| service 的通用异常放在 `contract/result` | `app/service/error` | `ApplicationServiceException`、`ApplicationServiceFailureType` |
| ui 的后台任务工具在控件包，任务交互在窗口包 | `app/ui/task` | `DesktopTaskExecutor`、`DesktopTaskHandle`、`TaskInteractionPresenter` |
| ui 的通用任务恢复与 SSH 救援混在 `recovery` | `app/ui/task`、`app/ui/server` | `TaskRecoveryPane` 归 `task`；`SshRecoveryDialog` 归 `server` |
| ui 的 Mod 页面挂载放在窗口包 | `app/ui/mod` | `ExtensionPagePane` 与页面注册类就近放置 |
| ui 的调试窗口放在设置包 | `app/ui/debug` | `UiDebugDialog`、`UiDebugPreviewHost`；普通设置页面继续归 `setting` |

归包须结合实际依赖，不能以扩大可见性来代替职责整理。例如当前包内可见的 `RepositoryTransactionExecutor` 同时承载通用事务和服务器写入，迁移时分别核对所属职责并复用既有实现；`DesktopThemeBindings` 与控件工厂有包内协作，首轮与控件一起归 `control`，不单凭名称将它拆到别处。

当前 Windows 更新包有 18 个类、卸载包有 14 个类，但各自围绕同一功能，首轮保留，不因类多自动拆包。文件模块当前三个生产类可先直接归根包，后续功能扩大后再依据实际需要分类。类归包本身不扩大为全仓库私有名称缩短；平台公开 API 的命名简化按本节单独落实。

用户确认的是先按这套方法改造，再审阅实际结构并进行细微调整。已列包名和功能归属不再作为未决定选项反复讨论；实现中发现真实职责、可见性或依赖问题时据实处理并说明，涉及功能边界或公开合同变化时单独明确范围。

<a id="voice-models"></a>

### 3.5 语音模型平台能力与统一模型清单（已确认规格）

#### 已确认目标与交付范围

主 APP 在既有文字、视觉能力基础上增加语音模型能力，由平台统一提供配置、能力验证、用途选择以及完整可用的公开调用入口与接口，供后续 APP 功能与 Mod 使用。**语音平台能力是 1.2 要实现的内容，调用入口必须实际接通；不以已有业务场景或现有业务调用方为前提，也不只停留在远期候选或目录占位。**

**文字、视觉、语音是同等级的正式平台能力，均通过统一 AI 服务体系提供标准调用入口，调用方法和使用流程基本一致。** 调用方沿用相同的模型用途选择、任务上下文、取消及错误处理方式，按所需能力提交对应输入并接收结果。语音不能成为只有配置、需要另找底层实现或等到出现业务调用方才补齐的特殊分支。

当前没有业务模块调用语音能力，本期也不为消费该能力专门开发新的 APP 业务功能或 Mod，例如语音控制部署、业务听写、结果朗读或实时语音对话。**暂缺的是业务调用方，平台调用入口仍须实现并可用。** 模型配置及能力验证界面属于平台交付范围，公开入口应接通实际模型调用、结果处理和验证；后续业务模块可直接接入，无需等到出现调用方时才补实现。

**语音范围已经敲定：只做语音转文字（语音识别），不做文字转语音或双向语音对话；完整音频提交与实时流式识别均在 1.2 实现。** 不将实时识别留给下一期，也不将“流式返回一份已上传文件的文字”当作实时音频输入已经支持。

#### Java 原生接入与两种识别方式（已确认）

内部继续使用项目自己的统一 Java AI 服务，不将“Java AI”当作 JDK 自带的识别模型或必须引入的第三方框架。底层采用 Java 原生网络能力：完整文件走 JDK `HttpClient`，实时会话走其 `WebSocket`；识别由配置的模型服务完成。复用现有 JSON、任务及凭据设施，第一版不为此引入整套 AI 框架或厂商 Java SDK。

第一版实现 **OpenAI 的文件转写与实时转写协议**，其他厂商的独立协议不纳入本期。模型地址和 API Key 仍由统一配置管理；兼容文字请求或文件转写的服务不一定兼容实时转写，必须分别验证，不能仅凭“OpenAI 兼容”标签作出承诺。

| 方式 | 标准入口应支持的流程 | 底层协议及验收界限 |
| --- | --- | --- |
| 完整音频提交 | 提交完整音频及格式信息，按选定模型完成转写，返回文字结果；支持任务取消、超时与资源释放 | HTTP 文件转写接口，按协议构造音频上传请求；不是把音频塞入现有文字 JSON 请求就算接入 |
| 实时流式识别 | 开始会话、分块发送音频、接收临时及最终文字、结束输入并等待最终结果、取消并关闭会话 | WebSocket 实时转写协议；结束输入与取消是不同操作，不用反复上传独立短文件冒充同一实时会话 |

实时合同须明确音频格式、片段与结果关联、顺序、有界缓冲与背压、错误和断连后的状态。最终结果可以分段到达，调用方应能识别所属片段及是否定稿；取消后释放连接和缓冲，不继续投递正常识别结果。不得在结果未知时静默重发整段音频或更换模型继续拼接，避免重复结果和重复调用。

具体受支持格式、采样参数、大小/时长限制及会话事件按选定协议和模型能力落实，作为实现规格记录；这些不是重新讨论是否实现识别或实时模式。首期直接接受约定格式的音频，格式或容量不符合时在发送前拒绝，不新增通用转码引擎、录音界面、麦克风管理或语音业务 Mod。使用受控音频输入验证公开接口。

以下只是简单名称的接口示意，具体类型及重载在 S4-01 落实，现有 AI 配置修订合同保留：

```java
ai.call(voiceRequest, task);                 // 完整音频
var session = ai.openVoice(options, listener, task);
session.send(audio);                        // 发送音频块
session.finish();                           // 结束输入，等待剩余结果
session.cancel();                           // 取消并释放会话
```

实时会话固定所选模型及配置修订，不在途中偷偷切换。`finish()` 停止接收输入并等待剩余结果后关闭，取消停止正常回调并释放资源；终态后不能继续发送音频。临时/最终结果携片段标识、顺序和状态；缓冲有上限，发送过快反馈背压。中断保留已确认结果及未知状态，不自动重发整段音频。实际异步返回形式由 S4-01 统一，不把示意方法写成已实现 API。

协议依据：[JDK 21 HttpClient](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.html)、[OpenAI 文件转写](https://developers.openai.com/api/docs/guides/speech-to-text)、[OpenAI 实时转写](https://developers.openai.com/api/docs/guides/realtime-transcription)。实施时核对当时协议，不在本计划硬编码某个模型名称或把第三方兼容声明当作实测结果。

#### 语音能力的历史代码基线

- 当时模型能力类型 `AiCapabilityType` 只有 `TEXT` 与 `VISION`，分别记录文字与视觉能力；平台公开用途 `AiPurpose` 为 `LANGUAGE`、`APPROVAL`、`VISION`。
- 当时 `AiMessage` 接收文字和图片附件，`AiResponse` 返回文字结果；尚无音频请求、音频响应及相应能力验证。
- 当时 `ModelHttpCall` 使用 JDK HTTP 客户端发送模型 JSON 请求，可复用网络接入方式；不能据此声称已实现音频上传或 WebSocket 实时转写。
- 当时 `AiModelInventoryPane` 已实现通用清单与用途编辑的左右列表，支持添加、移除、启用和调用顺序调整，可沿用这套交互。

以上只说明可复用的历史基础，不表示增加枚举项就完成语音功能。当前双协议实现及配置接线的验收见 S4。

#### 一个通用模型清单，多项能力分别标明

所有模型仍进入同一个通用清单，不按文字、视觉、语音各复制一份独立模型库。一个模型配置可以具备多项能力，并被多个用途引用；向用途列表添加模型只改变引用和顺序，不复制模型地址、凭据或配置。

<a id="voice-config"></a>

**一个模型记录、按协议配置连接。** 当前模型记录保存共同的名称、模型 ID 和凭据引用，以及按能力需要填写的可选完整地址，各能力独立验证：

| 配置 | 用途 |
| --- | --- |
| 文字/视觉地址 | 保留现有模型调用 |
| 文件转写地址 | 完整音频 HTTP 上传 |
| 实时转写地址 | WebSocket 实时会话 |
| 各能力验证状态 | 分别记录未验证、可用、不支持及验证失败原因 |

只有语音能力的模型可登记并验证，不要求先通过文字测试。完整提交与实时识别若使用不同模型 ID，在同一个清单建两条记录，不伪装成同一模型；同一模型的多用途仍只引用该配置，不复制凭据。

标准服务可提供地址填写模板并展示最终地址，保存的是明确配置；不靠替换文字 URL 后缀盲猜第三方路径。HTTP 与 WebSocket 按协议分别校验，必需查询参数由适配器明确处理，凭据继续走平台凭据设施，不写入地址或借重定向发送到未配置位置。

**模型加入流程：保存配置 → 标记未验证 → 用户选择验证能力 → 通过后允许加入对应用途列表。** 登记或验证通过均不自动加入主模型、审批、视觉或语音调用列表。显式能力验证属于配置操作，不是从通用清单随意挑选模型执行业务。改变地址、模型或凭据使受影响验证结论失效；纯显示名称调整不使能力失效。

当前 `PlatformModelService.save` 保存配置，`verify` 独立验证所选能力。纯语音配置不经过文字/视觉挑战；实时验证实际发送测试音频并核对对应结果，不以连接握手成功标记支持。文件/实时验证彼此独立，一个失败不能将另一个未经测试的能力写为可用。

每个模型应明确显示其已验证能力及尚未验证或验证失败的状态。**完整音频转写与实时音频转写分别标注、分别验证**，允许同一模型支持其中一种或两种；不能因模型支持文字、图片或文件转写，就推定支持实时音频。网络失败、凭据错误和协议不匹配应与明确不支持能力区分。验证结果须对应当前模型配置，配置变化后不能继续把失效结果显示为可用。

模型能力与调用用途分别管理：文字、视觉、语音表示处理能力；审批继续作为独立调用用途。模型通过文字验证并不自动加入审批列表，具备语音能力也不自动进入语音调用列表。

#### 沿用左右列表配置实际调用模型

| 界面位置 | 已确认行为 |
| --- | --- |
| 左侧通用模型清单 | 展示全部已添加模型及各项能力状态；选择用途时继续保留原清单 |
| 中间添加/移除操作 | 将同一模型加入或移出当前用途的调用列表；未满足该用途所需能力时说明原因，不作为可执行候选加入 |
| 右侧用途调用列表 | 展示当前用途实际配置的模型，沿用启用、排序与保存机制；语言、审批、视觉用途保留，增加语音用途配置 |
| 列表顺序 | 通用清单的展示顺序与每个用途的调用顺序分别保存，互不替代 |

调用接口按请求所需能力及对应用途列表选择模型，遵循该列表的启用状态和调用顺序；语音用途列表可包含分别支持完整提交或实时方式的模型，但每次请求只使用支持该方式的候选，界面标明适用方式及不匹配原因。用途列表为空或没有匹配模型时返回明确的未配置/不可用结果，不从通用清单自动挑选未经配置的模型，也不把实时请求降为完整文件请求。

现有任务归属、凭据管理、取消和未知结果处理继续复用。完整提交与实时会话都受相同的任务、用途和授权边界管理；结果、用量及格式校验按各自协议表达，不机械照搬文字 Token 的输入输出约定。

统一调用方式不要求文字、图片和音频具有相同的数据格式。音频参数、响应和流式差异通过同一套标准合同明确表达；调用方使用 `AiService.call(VoiceRequest, ...)` 或 `openVoice`，不直接操作提供方客户端，也不另走一条缺少统一配置和任务管理的语音调用通道。

### 3.6 开发阶段数据库直接重建（已确认规格）

1.2 仍处于开发阶段。用户已明确不要求兼容上一代本机开发数据库：包括语音能力、受管链接及操作记录、删除 AI 说明开关需要的数据在内，直接以新结构更新建库定义，开发切换时清理旧库并重新初始化，不迁移旧开发数据，也不为每一轮开发积累旧结构兼容链。

- **结构与代码：** 新建库直接得到本期完整结构；不为旧 APP 开发版本新增逐版升级脚本、旧字段读取分支或双结构支持。现有仅为这类旧版本兼容而存在的代码、脚本和测试，实施时核对并清理；当前正确行为的验证保留或随新结构更新。
- **数据范围：** 清理范围为 APP 本机开发数据库及配套材料。旧服务器列表、模型配置、凭据与任务记录，以及同库存储的 Mod 数据等随旧库清理，不另加迁移保留流程。远端服务器上的业务数据库与文件不属于该清理范围。
- **保留能力：** 首次建库、当前结构与数据库身份校验仍保留。Mod 自身数据版本升级是独立的平台能力，本次不因拒绝旧 APP 开发库兼容而整体删除；也不由本决定推出公开 API 或远端协议的兼容政策。
- **重建方式：** 这是开发切换时的明确清理与初始化步骤，不是软件遇到数据库错误就自动删除重建的运行策略；旧库结构不匹配、材料损坏或身份冲突仍须按实际错误处理。

当前实现中，`DatabaseBootstrap` 要求 `windowstolinux.mv.db` 与 `db-access.bin` 成对存在；只删数据库主体会因访问材料残留而拒绝启动。新建前也会检查数据库残留文件。实施时先使 APP 退出并释放连接、锁及资源，确认实际本机开发数据目录，再处理确属该库的数据库文件、配对访问材料和需清理的残留。不能通过删除整个工作区或所有配置目录代替核对，也不删除正在使用的锁来强行重建。

当前 `PlatformDatabase` 首次初始化读取建库脚本，随后启动校验数据库身份、结构记录和脚本摘要。1.2 可在这一基础上直接更新当前结构；语音分协议配置、能力及用途记录、受管链接和操作依据均随最终合同落地；删除 AI 说明开关复用桌面偏好存储，初始化及重开行为一并验证，不额外建设旧库数据转换通路。当前建库脚本已按 1.2 更新；实际开发库切换与重建验收见 S5 和[第 6.6 节](#database-delivery)。

### 3.7 平台原生接口与可选封装 Mod（已确认）

1.2 继续采用 1.1 已确认的职责边界：Mod 作者自行实现自己的业务数据库结构、数据操作和界面，主 APP 提供基础接口及必要的运行管理。这里的“作者自行实现数据库”指业务表、SQL、事务及相应生命周期逻辑，不是要求每个 Mod 另行安装 H2、创建平台数据库文件或管理数据库引擎。1.1 的承接入口见[数据库设计](PHASE-1.1.md#database-design)与[平台公开能力](../Mod.md#platform-api)。

| 能力 | 主 APP 提供 | Mod 作者负责 |
| --- | --- | --- |
| 数据库 | 统一 H2 引擎、数据库生命周期、所属 Schema 和受管标准 JDBC 连接，以及已有初始化/版本生命周期入口 | 自身业务表、SQL、事务、初始化与迁移逻辑，按合同关闭连接及相关资源 |

当前 [ModDatabase](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/db/ModDatabase.java) 已提供受管 `java.sql.Connection`；[ModPage](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/ui/page/ModPage.java) 由作者创建 `JComponent`，[UiService](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/ui/UiService.java) 负责登记和挂载。这些是当前接口事实，不表示后续封装 Mod 已存在或本轮重新完成运行验收。

**这一原则适用于全部公开 API。** 主 APP 不为降低某一技术的学习成本而内置面向 Mod 的业务数据库封装层或组件框架；作者可以直接使用基础接口，也可在后续选择复用 Mod。原生接口仍保留必要的受管合同，不意味着直接暴露引擎管理连接、秘密、宿主实现类或原始 SSH 客户端，也不撤销统一文件 API、语音协议适配、平台审批等必要能力。

主 APP 自身的数据库访问、设置页面和内部 Swing 控件继续按已有职责实现；本决定针对向 Mod 提供的能力边界，不要求为此移走主 APP 自用代码或取消必要的公共审批交互。

### 3.8 现有 API 的重载补齐与行为对齐（已确认规格）

本节基于现有 `appapi` 公开接口、请求类型、平台实现及调用方检查，承接第 3.1 节的同名重载规则。用户已认可下表结论：上传/下载和目录选择优先补齐，任务进度及第一页查询随公开 API 简化实施，传输停滞策略保留按需范围。以下现状是计划编制时的源码基线，链接指向当前对应文件；新增重载的实际状态由阶段验收记录说明。

| 能力 | 当前代码与缺口 | 本期安排 |
| --- | --- | --- |
| 上传、下载 | [RemoteSession](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/linux/session/RemoteSession.java) 只有 `upload(request, grant)`、`download(request, grant)`；[TransferRequest](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/linux/transfer/TransferRequest.java) 不含冲突方式，实际同名冲突转平台交互 | 优先补同名重载：未传方式时询问，显式传入时按方式执行。落到统一文件 API，既有会话调用路径同步衔接，底层仍复用原传输实现 |
| 目录选择 | [SourceService](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/file/FileService.java) 只有 `selectDirectory(title, task)`；[平台实现](../../src/app/service/src/main/java/gold/debug/windowstolinux/app/service/file/PlatformFileAccess.java) 实际调用目录选择器 | 优先补接收明确目录路径的同名重载。适用于调用方已知目录的情形，不再让用户重复选择；仍核对任务授权、账户权限和物理目录身份 |
| 任务进度 | [TaskContext](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/task/run/TaskContext.java) 仅接收 `progress(text, Optional<Double>)`，生产调用方存在反复传空值的情形 | 补 `progress(text)` 和 `progress(text, fraction)`，分别表达纯文字状态与明确比例；复用原校验和发布逻辑 |
| 第一页查询 | [ServerService](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/server/ServerService.java) 的 `list`、`listConfigured` 及 [TaskService](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/task/TaskService.java) 的 `list` 均需显式传游标，即使查询第一页 | 补省略游标的同名重载，保留显式页大小和原权限范围；后续页仍传原游标，不改成无界“查询全部” |
| 传输停滞 | [PlatformLinuxService](../../src/app/service/src/main/java/gold/debug/windowstolinux/app/service/linux/PlatformLinuxService.java) 在 `SFTP_STALLED` 后停止当前连接并询问重试/终止，与同名冲突是独立交互 | 按需增加带有限重试策略的重载；未传策略仍沿用原交互。若本期调用方需要自动处理停滞，则在 S3-06 落实，否则记录保留原行为，不直接列为本期新增必做能力 |

#### 重载形式与保留的边界

下例用当前名称示意；不是声明已存在的新方法，也不要求在旧 `RemoteSession` 与新文件服务各自公开、维护两套同义能力：

```java
upload(request, grant);          // 未传同名冲突方式，发生冲突时询问
upload(request, grant, choice);  // 使用明确方式，仍校验操作授权
download(request, grant);
download(request, grant, choice);

selectDirectory(title, task);    // title 为 String，弹窗选择目录
selectDirectory(path, task);     // path 为 Path，核对并取得指定目录

progress(text);
progress(text, fraction);

list(limit, task);               // ServerService 第一页
list(cursor, limit, task);       // ServerService 后续页
```

- 上传/下载复用第 3.1 节文件冲突的覆盖、保留副本、不处理规则；涉及目录冲突的统一文件调用按两级规则执行，单文件传输不额外弹出目录选择。显式处理方式不是审批许可，调用方不能借重载取消任务、来源摘要、目标身份或操作授权校验。受影响的审批描述须与真实操作一致，不能传入明确方式却仍记录为“稍后必定询问”；涉及链接时须在统一入口明确 File / Link 实际对象语义。
- 指定 `Path` 是取得已知目录，不是指定选择窗口初始目录，也不是取得任意路径访问权。平台验证真实任务与既有授权后登记目录句柄；无权访问时明确失败，需要新的操作授权时仍由统一平台处理，不以没有目录选择弹窗推定所有审批都可跳过。这个本机重载不把 Windows `Path` 当作 Linux 远端路径。
- 无比例进度表示比例未知，不填写为 0 或 100%；显式比例沿用 0～1 的边界及数值校验。相同业务含义只走一套底层逻辑，不复制资源和任务检查。
- 第一页重载只省略空游标，不省略页容量及当前方法所需的任务。任务列表的签名按自身合同省略游标；`list` 与 `listConfigured` 的可见范围不同，仍保留为各自的方法，不因“都是列表”合并权限。
- 有限重试策略与冲突方式分开表达，不能共用一个“自动处理”布尔值。需要实现时明确次数/期限、终止条件与取消行为，只在原传输身份、暂存、来源及服务器可核对时续传；结果未知时先核对，不盲目重发副作用，也不新增无限重试。

#### 两处必须同步的实际行为

1. **文件用途说明只用首模型。** [PlatformAiService](../../src/app/service/src/main/java/gold/debug/windowstolinux/app/service/ai/PlatformAiService.java) 的文件说明入口先检查开关，再从实际 LANGUAGE 用途列表取首个启用模型；失败保留人工确认，不暗换第二个，不从通用清单挑模型。普通 AI 调用原有候选路由及 `expectedRevision` 约束保留，不新增任意指定模型的公开后门。相关专项检查对应 S3-09。
2. **“不处理”与“取消”分开。** [SftpDestination](../../src/app/linux/src/main/java/gold/debug/windowstolinux/app/linux/sftp/SftpDestination.java) 的 `TransferConflictChoice.SKIP` 返回明确失败及 `SFTP_CONFLICT_SKIPPED`；主动取消仍返回取消。统一目录操作跳过单项后继续独立项，最终报告部分失败。S3-05、S3-06 同步了选择、审批描述、界面和调用方；停滞选择的 `TERMINATE` 保留原合同，不机械替换。

#### 已有重载与不扩大的范围

- [AiService.call](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/ai/AiService.java) 已有普通调用与携带 `expectedRevision` 的重载；保留其配置修订约束，不为统一外观重复添加同义入口。
- [SourceService.workspace](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/file/FileService.java) 和 [ProcessService.start](../../src/appapi/src/main/java/gold/debug/windowstolinux/appapi/task/process/ProcessService.java) 已有自动身份与显式预留身份的重载；保留原任务归属及首次创建约束，不能解释为任意复用旧资源。
- 数据库连接、凭据使用及资源关闭沿用现有显式合同，不统一新增“普通/高权限”重载。SSH 命令仍需要精确审核和真实许可，不仅为减少参数而省略权限或业务修订信息。
- 以上是必要的基础 API 调用便利和交互选择，不扩大为主 APP 内置 SQL/Swing 业务封装框架，也不强制 Mod 作者修改自己的公开 API。

## 4. 功能依赖与设计边界

以下为已确认方案实施时需要保留的边界：

- **平台 API 与封装 Mod：** 全部公开 API 按第 3.7 节提供基础能力和必要受管边界；业务数据与界面由作者实现。SQL、Swing 的高层复用放在后续可选 Mod，本期不开发，也不因接口原生而下放任务、权限和资源管理职责。
- **通用操作与业务规则：** 文件读取、摘要、受管目录清理可统一；部署排除规则、`source.include`、配置解析、发布目录布局及业务归档格式仍由所属业务决定。通用归档机制是否提取另行评估。
- **本机与远端：** 远端资源必须关联服务器身份，不能只用路径字符串区分，也不能直接以本机 Windows `Path` 解释 Linux 路径。File / Link 分别按实际目标/链接对象接线，目录合并与文件覆盖分开处理；权限、链接支持和原子替换能力按实际环境表达。
- **文件 API 与后续界面：** 1.2 交付账户实际权限内的通用文件 API；资源管理器界面由后续 Mod 提供，本期不开发该 Mod。目录查询能力的接口验证不依赖未来页面。
- **APP 操作与外部系统操作：** 经统一文件 API 发起的操作按第 3.1 节维护关联：移动/重命名跟随原件、目录复制建立副本内部指向、覆盖同步目标身份；底层使用 Windows 或 SSH/SFTP 不改变职责。独立系统操作及未接入文件 API 的脚本由系统自行处理，不增加监听、拦截或事后自动修复。
- **授权与恢复：** 统一入口需要保留原任务绑定、资源归属、操作范围、取消、未知结果和真实清理语义；断连或结果不明不自动转换为成功或重新执行副作用。
- **已有传输机制：** 优先复用当前 SFTP 的冲突、校验、暂存发布、续传和恢复实现，再按需要调整职责，不先重写传输状态机。
- **连接与文件协议：** SFTP 复用 SSH 的连接、认证和加密会话，文件通道与文件操作实现独立；界面和 Mod 统一使用平台能力，不能另建客户端绕过任务和权限。
- **SSH 救援与通用恢复：** SSH 救援包只收专属状态、交互、协议及存储；通用任务恢复和共享平台服务按原职责组织，不因救援入口接入服务器页而接管其他业务。
- **平台自有文件：** 数据库引擎管理的文件、启动应急日志和类加载等特殊生命周期不预设必须经过任务型资源服务；可复用的文件原语与各自所有权分开评估。
- **依赖方向：** 保持 Mod 通过 `appapi` 使用平台能力；资源实现不反向依赖业务 Mod。涉及模块依赖变化时同步核对现有架构约束，避免循环依赖。

## 5. 分阶段执行计划

### 5.1 执行入口与完成口径

用户已启动 1.2 完整源码开发目标，按 S0～S6 实施并登记实际证据。关键未决范围、数据效果或权限问题暂停对应步骤等待确认；常规实现选择自行决定并汇报。指定开发库切换按 S5 的已确认范围执行。

1. **先核对基线。** 读取适用指令、实际工作区与已有进度，保留现有修改；与计划编写时不同的已完成事项据实登记，避免重复开发。
2. **按任务卡推进。** 默认按第 5.2 节阶段顺序、阶段内编号执行；达到开始条件后完成该卡的“实施/产物”和“完成检查”，再进入依赖它的任务。可编译迁移所需的引用调整与该批改动同时进行。
3. **逐项记证据。** 只有实现及该卡要求的必要验证完成才勾选；记录受变范围、实际检查结果和下一步。文件移动、编译通过、写了方案或登记环境缺失都不代替相应功能验收。
4. **区分状态。** 实现与本机/受控验证、真实环境验收分别记录。记录“待真实验收”的任务可以完成状态登记，但对应真实验收仍未通过，不继承历史的 34 项或 22 项测试作为新功能证据。
5. **只暂停受影响步骤。** 实施中若出现本计划未覆盖、实际影响数据效果的必要决定，只暂停对应分支；已确认的目录两级选择和 File / Link 分工不再重复询问。缺少模型、服务器或云控制台时登记未验收条件，继续独立实现、S5 集成及 S6 回归；第 7.3 节未纳入的扩展不阻塞本期。不用占位接口、放宽检查或静默回退绕过问题。
6. **按原范围收尾。** 每阶段达到退出条件再标记阶段完成；最终对照第 7.1 节逐项核对。未完成工作、失败或必要验收缺口继续保留，不能因运行时间或预算接近结束就把目标标成完成。

已确认名称、分包及同名重载方向直接执行。第 7.2 节的普通实现选择由实施者结合现有合同解决；真正影响数据效果、范围或清理目标的缺失决定只在对应步骤前澄清。当前计划不要求并行代理、额外技术栈或新建 Maven 模块。

后续实施若跨多轮，按项目届时生效的进度工作流接续当前记录，不覆盖其他未完成任务；记录任务编号、当前阶段、产物、验证、阻塞和下一步即可，不反复复制整份规格。本文维护规格与任务定义，既有当前进度记录维护实际执行状态，两者保持一致。

### 6.4 语音模型平台能力实施与验收要求

**合同：** 1.2 交付语音识别的完整提交与实时流式两种入口。内部统一 Java AI 服务，底层 Java 原生网络接入 OpenAI 协议；不做合成，不要求已有业务调用方，也不为消费能力开发新业务模块。实际实现及受控验证见 S4 阶段记录。

以下对应 S4 的交付与验收，不能只增加枚举、配置标签或不可调用的接口：

1. **标准合同与能力匹配。** 两种入口均与文字、视觉复用模型配置、用途、任务、凭据、取消和错误机制。请求明确采用完整文件或实时方式，模型必须匹配；公开接口不向调用方泄露提供方客户端。检查格式、大小/时长及采样限制，不能把结果文本流当作实时音频输入。

3. **实时会话闭环。** 从公开入口建会话并冻结模型/配置，分块输入、接收临时/最终文字；finish 取得剩余结果后关闭，cancel 停止正常回调并释放资源。覆盖片段关联、次序、缓冲上限、背压、拒绝连接、中断及最终结果缺失；终态拒绝后续发送，不静默换模型或重发未知会话。
4. **能力验证与存储。** 同一清单记录可选的文字/视觉 HTTP、文件转写 HTTP、实时 WebSocket 完整地址、独立能力与配置修订。允许先保存未验证配置，纯语音不要求文字探测；逐项显式验证，实时须有音频输入和识别输出。相关配置变化撤销对应结论，仅改显示名保留；区分未验证、不支持与网络/凭据/协议失败，验证保存及重开。
5. **用途列表与路由。** 模型清单及显式能力测试不授予业务调用资格；用户加入右侧实际用途列表、启用并保存后才能路由。验证添加、移除、排序和重开；共享配置而不影响语言/审批/视觉。覆盖仅文件、仅实时、双能力、空列表和不匹配，不从清单自行挑模型，也不把实时降级为文件。
6. **平台接线和现有行为。** 使用独立接口测试及受控音频验证两种完整调用路径；验证文字/视觉和审批调用仍正常。不要求录音界面、业务听写或语音 Mod，配置与能力验证界面本身须可用。
7. **真实环境记录。** 有合适提供方、音频和调用授权时，对完整提交及实时识别分别记录协议、模型、环境与结果。某提供方只通过其中一种，不能把另一种也标为支持；缺少环境时保留真实能力待验收状态，可继续不依赖它的开发与集成，不把模拟响应写成模型实测。

受控 HTTP/WebSocket 及真实平台入口证明协议、配置和生命周期；真实提供方两种识别效果另列待验收条件，不以受控响应替代。
