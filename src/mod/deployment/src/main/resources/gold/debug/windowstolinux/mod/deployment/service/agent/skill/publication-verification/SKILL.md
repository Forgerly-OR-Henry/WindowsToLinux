---
name: publication-verification
description: Assess formal application publication, current health and cleanup evidence when choosing or reviewing activation and completion actions.
---

Use when planning activation, evaluating a publication result, reviewing health or cleanup commands, or deciding whether deployment may finish. Consult the current graph, sealed artifact and binding identities; read the fixed product contract only for a specific lifecycle uncertainty. Built-in publication and model-authored commands remain available subject to their actual prerequisites. This skill prescribes no language, recipe or command sequence.

A declaration, successful build, candidate invocation, command exit zero or deployment model statement does not prove published health. Verify the actual current release, listener or typed runtime behavior, application health and ownership expected by the original graph. HTTP reachability is distinct from browser or business behavior; keep any required unobserved acceptance explicit. Changed commands or inputs require new independent exact approval.

Managed bindings are applied to the copied formal release after candidate sealing and replace the logical access path. FILE exposes a persistent directory tree; its optional directory seed initializes it once, while an empty seed creates an empty directory and later publication preserves existing data. CONFIGURATION exposes an immutable regular file whose seed bytes must match its reviewed digest. Candidate content at the logical path is not an implicit seed. When a required runtime consumer depends on such a path, assess the post-binding object shape and consumed content against the actual current release and binding identities. Candidate probes or a healthy homepage do not establish that evidence; unavailable facts remain unverified. Choose evidence and actions from the original requirements without changing storage types or inputs by assumption.

Configuration and endpoint declarations do not rewrite an artifact consumer. Check its startup entrypoint, literal argv, consumed configuration keys and override priority against the current graph; component dependencies should reflect actual runtime consumption. A change to a target or configuration invalidates earlier evidence for the affected consumer chain even when the artifact is unchanged. Independently healthy components or a healthy homepage do not prove their connection through the actual business entrypoint. Select evidence that exercises the required chain under the current formal configuration; retain missing coverage as unverified.

Reviewing a proposed observation is pre-execution: that pending invocation has no result receipt yet. Assess its complete executable action, fixed SYSTEM implementation semantics, current bindings and existing independent receipts; hashes and DATA do not themselves prove remote execution or grant authority. Keep this authorization question separate from the later actual health result. Respect the actual refusal and discussion status; a closed DENY must not be reopened for the same request. Unavailable verification does not by itself prove unhealthy business behavior or justify a disruptive repair.

Finish only from actual verified publication and settled task-owned resources. Cleanup must preserve formal application, configuration, persistence and shared references, and target only original temporary candidates with verified identities. Failed, denied, occupied or UNKNOWN effects cannot be reported as completed cleanup. Formal commit and receipt gates stay mandatory even if this skill was never loaded.
